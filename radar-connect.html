5. 连不上时按顺序查

地址、网络、协议三类问题
  1. 地址写成了 127.0.0.1 但雷达在另一台机器 —— 要写那台机器的局域网 IP， 且浏览器所在设备要和它同一网段（手机同 WiFi 也算）。
  2. 雷达服务没起 / 端口不是 8766 —— 在雷达那台机器上确认 ws://0.0.0.0:8766 已在听（不是只绑 127.0.0.1），防火墙放行该端口。
  3. 页面是 https 却连 ws:// —— 浏览器会直接拦掉混合内容；用 http 打开本页 （见 README 方式 B），或让雷达侧上 wss://。
  4. 连上了但一直"还没收到帧" —— 雷达侧发的是二进制/非 JSON，或字段名不对。 必须是每帧一个 JSON 对象（数组也行），见下方约定。
  5. 连上也有帧，但 x 恒定不变 —— 大概率是没人站在探测区，或采集端把 x 写成了常量； 先让人站在中间左右走动看曲线。
  6. 想一次看清卡在哪一环 —— 在雷达那台机器上跑 python tools/check_radar.py <雷达地址>， 它会分别报 TCP 连通 / WebSocket 握手 / 帧率 / 字段齐全 / 数据质量，一眼看出是网络、协议还是数据的问题。
  7. 雷达给的不是 WebSocket（串口 / UDP / TCP / HTTP 接口 / 厂商 SDK）—— 不用改游戏： 跑 python tools/radar_bridge.py 把雷达原始输出转成 ws，再连 ws://127.0.0.1:8766。第一次用加 --print-sample，先确认它收到的报文长什么样。
数据帧格式（与硬件同学对齐用） 
{"ts":1730000000000,"x":0.42,"height":0.0,"jump":0,"crouch":0,"confidence":0.93,"raw":{}}

ts          采集时间戳（毫秒，采集时刻而非发送时刻）—— 用来算延迟
x           横向位置，归一化 [-1,1]，左负右正（极性装反没关系，游戏会现场学）
height      起跳高度 0~1（当前不参与判定）
jump        起跳标志 0~1 / bool
crouch      下蹲标志 0~1 / bool
confidence  本帧可信度 0~1，低于 minConfidence 会被游戏丢弃
raw         原始数据（可选），调试面板会展示
也支持一次发多帧：发送一个 JSON 数组，游戏会顺序处理。
本页是开发/联调页，纯静态、无依赖，双击即可打开（file://）； 但校准存档需要 localStorage，建议用 python -m http.server 打开。
