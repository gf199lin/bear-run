# 雷达数据评估 + 采集方案 + 开局校准教程设计

- 评估对象：`lr-move-frames.csv`（3092 帧）/ `lr-move-actions.csv`（30 个动作）/ `lr-move-dataset-README.md`
- 硬件：矽典微 DEV202H（ICL1122，1T2R），3 个站位 0.70 / 0.85 / 1.00 m
- 游戏侧对应代码：`radar-runner/js/InputSource.js`（`RadarDecoder` / `RadarInputSource`）、`config.js` 的 `RADAR` 段
- 结论（一句话）：**这批数据可以当"反例证据"，但不能用来标定左右方向；上下（跳/蹲）数据完全没有。需要按第 2 节重采一批。**

## 1. 数据评估结论

### 1.1 基本量

| 项 | 实测值 |
|---|---|
| 总帧数 | 3092（3 段 × ≈1031 帧） |
| 实际帧率 | **7.75 Hz**（帧间隔中位 129.0 ms，min 129.0 / max 130.0，非常稳） |
| 检出率（`n_pts` 非空） | 0.70 m **44.7%** / 0.85 m **48.3%** / 1.00 m **31.8%**，合计 **41.6%** |
| 每帧点数 | 2 点 584 帧、3 点 296、4 点 167 … 最多 13 点；**中位只有 2 点** |
| 帧标签分布 | IDLE 2468 / LEFT 312 / RIGHT 312 |
| 动作数 | LEFT 15 / RIGHT 15（`actions.csv`） |
| 帧级事件 | `TARGET_BACK` 116、`TARGET_LOST` 113、**`JUMP` 60、`DUCK` 19**、`LANE_RIGHT` 15、`LANE_LEFT` 3 |
| 动作窗口长度 | 中位 2.59 s（min 2.46 / max 2.59，很齐） |
| 动作间隔 | 中位 9.07 s |

### 1.2 致命问题：左右方向符号不可用

用 `px_delta_m` 的符号当"左右分类器"（<0 判左）：

```
真 LEFT   预测 LEFT=13   预测 RIGHT= 2
真 RIGHT  预测 RIGHT= 3   预测 LEFT=12
准确率 = 53.3%   （≈ 抛硬币）
左移召回 87% / 右移召回 20%
```

- **右移 15 次里 12 次被判成"向左"**。
- `px_delta_m` 中位数：LEFT **−1.056 m**，RIGHT **−0.288 m** —— **两个方向的中位数都是负的**，方向信息在符号上丢失了。
- 按站位看，符号还会漂移，说明这不是"整体反相"，而是**逐站位失效**：

| 站位 | LEFT 中位 Δ | RIGHT 中位 Δ | RIGHT 中 Δ>0 的个数 |
|---|---|---|---|
| 0.70 m | −1.219 | −0.337 | **0 / 5** |
| 0.85 m | −1.056 | **+0.093** | 3 / 5 |
| 1.00 m | **−0.058** | −0.497 | **0 / 5** |

### 1.3 第二个致命问题：静息基线严重偏离零点

人站着不动（IDLE 帧）时，`px_m` 不是 0：

| 站位 | IDLE `px_m` 均值 | 中位 | 标准差 |
|---|---|---|---|
| 0.70 m | +0.532 | +0.623 | 0.264 |
| 0.85 m | +0.567 | +0.620 | 0.189 |
| 1.00 m | **+0.971** | +1.034 | 0.228 |

站位越远，基线越偏。结合 README 里的"静息主回波方位角 +40°、横向偏 1.1~1.5 m"，说明**录制时雷达没有对准人**，人体落在 ±45° 视场边缘。

**这条对游戏是硬伤**：游戏车道判定是 `x ≤ −0.36` 进左道 / `x ≥ +0.36` 进右道（`config.js:356-357`）。如果静息基线本身就有 +0.5 以上的偏置，玩家"站着不动"会直接被判进右道，且左移需要走的距离远大于右移 —— 手感完全不对称。

### 1.4 第三个问题：左移动作的检出密度只有右移的 1/3

| 指标 | LEFT | RIGHT |
|---|---|---|
| 动作窗内检出帧数（窗口约 20 帧） | 中位 **5**（≈25%） | 中位 **15**（≈75%） |
| `px_range_m` 中位（可见位移幅度） | 1.281 m | 0.504 m |

左移时人往视场外侧走，目标更容易丢（与 README 自述一致）。

### 1.5 上下（跳/蹲）：完全没有可用数据

- 数据集**只有 LEFT / RIGHT**，没有独立的"跳"和"蹲"动作段。
- `frames.csv` 里虽然出现了 `JUMP`(60 帧) / `DUCK`(19 帧)，但那是 IDLE 期间的偶发事件，**没有对照组**（无"站着不动 + 跳一下"的配对标注），也没有对应的 `height` 真值 —— 无法据此定 `jumpThreshold`。
- README 也自述雷达**没有高度维度**，垂直起跳识别存在风险。

### 1.6 判决

| 用途 | 这批数据够不够 |
|---|---|
| 直接标定左右阈值/符号 | ❌ 不够（53.3%，比猜还差） |
| 标定"中位基线偏移" | ⚠️ 只能证明"必须现场定基线"，具体值不可用（站位相关） |
| 定跳跃/下蹲阈值 | ❌ 完全没有数据 |
| 证明"开局必须做现场校准" | ✅ **这就是最好的证据** |

**结论：必须补采。** 与此同时，**游戏侧不能等数据** —— 正确做法是把"方向符号 + 基线偏移"做成**开局现场校准**（第 3 节），因为符号本来就取决于玩家的站位和朝向，**任何人预先采的数据都无法替玩家定**。这也是"新手教程"存在的真正理由。

## 3. 游戏侧：开局"新手教程 / 雷达动作确认"设计

数据结论反过来给了教程一个**明确的技术目标**：在开局用玩家本人现场测出两件事 ——

1. **方向符号 `sign`**（玩家的"向右"到底是 x 变大还是变小）；
2. **静息基线 `x0`**（玩家站中间时 x 并不等于 0）。

校准后所有帧都过一遍 `x' = (x − x0) × sign`，再进 `RadarDecoder`。这样无论雷达装反、
玩家站偏，车道判定都能对齐。

### 3.1 为什么必须"现场"校准，而不是写死阈值

- 上一批数据里 0.70 m 和 0.85 m 站位的符号表现就不一致（0/5 vs 3/5 一致），
  说明符号/基线**随站位、被试、安装角度变化**，任何离线标定值都不能替玩家定。
- 因此教程不是"教学"，而是**每次开局的设备标定流程**（可跳过，用键盘兜底）。

### 3.2 步骤（5 步，数据驱动）

| 步 | 玩家动作 | 通过条件（用实测数字定） | 产出 |
|---|---|---|---|
| 1 | 站好别动 | 连续 **8 帧**（≈1 s @7.75 Hz）有效且 `x` 标准差 < **0.18** | `x0` = 该窗口 `x` 中位数 |
| 2 | 向左移一步 | `\|x − x0\| ≥ 0.35` 且保持 **3 帧**（**刻意不判方向**，只记哪一侧） | `sideA` = 走这一侧时的 `x` |
| 3 | 向右移一步 | 走到**与第 2 步相反的一侧**（`\|x − x0\| ≥ 0.35`）且保持 **3 帧** | `sideB` = 走这一侧时的 `x` |
| 4 | 跳一下 | 收到 `jump` 事件或 `height ≥ jumpThreshold` | `jumpOk` |
| 5 | 蹲一下 | 收到 `slide` 事件或 `crouch ≥ crouchThreshold` | `crouchOk` |

- 位移阈值取 **0.35**，正好贴着游戏的进道阈值 `enterThreshold = 0.36`（`config.js:356`）
  —— 保证"校准能通过的位移"在游戏里一定够换道。
- `sign = (sideB − sideA) > 0 ? +1 : −1`：**只看两侧是否落在基准线的两边**，不预设"左 =
  变小"。这就是"装反也能用"的原因（验收用例 4）——若第 2 步就判方向，雷达装反会永远卡在
  第 2 步，而装反恰恰是上一批数据的两种主要故障之一。
- 若 `\|sideB − sideA\| < minSpread` 判为**不可靠**，提示重试。注意默认 `moveDelta = 0.35`
  时其数学下界是 `2 × 0.35 = 0.70`，所以 `minSpread = 0.5` 实际**永不触发**；真正会走到
  "不可靠"的只有两条路：**半途改用键盘兜底**（第 2 步走了雷达侧、第 3 步用键盘完成，两侧
  不具可比性）、**两侧缺失**。
- 第 4/5 步若雷达不提供 jump/crouch（`height` 全程 0）→ 标记 `jumpOk = false`，
  **自动回落到键盘**（空格 / ↓），不阻塞流程。

### 3.3 断连与兜底

- 校准期间沿用已有的 `staleMs = 500` 掉线检测（`InputSource.js:365-368`）：掉线 → 提示
  "雷达未连接，已切键盘"，并允许用键盘走完流程。
- 全程监听键盘（← → 空格 ↓），键盘完成时 `sign = +1` 且标记 `source = 'keyboard'`，
  游戏内提示"当前为键盘模式"。
- 校准结果存 `localStorage`（`bear-run:calib:v1`），下次开局可直接"使用上次校准"。

### 3.4 接入方式（关键：不碰对方正在改的文件）

对方会话正在改 `js/InputSource.js`（`ReplayRadarInputSource`）。好消息是**不需要改它**：

- `RadarInputSource._handleFrame(frame)`（`InputSource.js:345`）是**实例方法**，
  且它把 `frame` 交给 `this.decoder.push(frame)`（`:355`）。
- 因此在新文件 `js/Calibration.js` 里给**实例**打一层装饰器，在进解码器之前改写 `x`：

```js
var orig = src._handleFrame.bind(src);
src._handleFrame = function (frame) {
  if (cal.enabled && frame) frame = { x: (num(frame.x) - cal.x0) * cal.sign, /* 其余字段原样 */ };
  orig(frame);
};
```

- 这样 `InputSource.js` **一行都不用改**，也不会跟对方会话冲突。

实际落地的装配（已实现并自检通过）：

| 文件 | 改动 |
|---|---|
| `js/Calibration.js`（新增 24.7 KB） | `RR.Calibration`（`bear-run:calib:v1` 存取 / `install` 装饰器 / `setEnabled` / `describe`）+ `RR.CalibrationWizard`（5 步状态机 + 自建 `.calib-overlay` DOM + 键盘兜底） |
| `index.html` | 加 1 行 `<script>`（`?v=` 同步）+ 菜单里 `#btn-calib` / `#calib-status` |
| `js/main.js` | 装配装饰器 + 菜单入口绑定 +（有存档）自动装载 /（无存档）开局 600 ms 后首启引导 |
| `js/config.js` | `RADAR.calib = { autoOpen, baseFrames, baseStdMax, moveDelta, holdFrames, minSpread, stepTimeoutMs }` |
| `style.css` | `.calib-*` 覆盖层样式（`z-index:40`，高于 `.overlay:20`；复用现有配色常量） |
| `js/Game.js` | **零改动** |

- 向导由自己的 `requestAnimationFrame` 驱动（`dt` 上限 0.5 s），所以**不需要碰 `Game.js`**；
  主菜单里也能直接校准（不必先进游戏）。
