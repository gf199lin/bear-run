# 双雷达双开 · 组员操作手册

> 目标：两台雷达各由**一个独立后台进程**负责，判定（换道 / 起跳 / 下蹲）全部在后台算完，
> 游戏只接收 `left / right / jump / slide` 结果。游戏里不需要配双雷达，也不需要调阈值。

---

## 一、先看懂要开几个窗口

```
  雷达A（管左右）──► radar_bridge.py --role lr --judge  ──┐
                                                            ├──► radar_hub.py ──► 游戏
  雷达B（管上下）──► radar_bridge.py --role ud --judge  ──┘        (单一路径 8766)
```

| 窗口 | 进程 | 干什么 | 判定 |
|---|---|---|---|
| 窗口 1 | `radar_bridge.py --role lr --judge` | 读左右雷达，判 `left/right` | **是** |
| 窗口 2 | `radar_bridge.py --role ud --judge` | 读上下雷达，判 `jump/slide` | **是** |
| 窗口 3 | `radar_hub.py` | 把两路合成一条给游戏 | 否，纯转发 |

关键点：**两个判定进程互不干扰**。`--role lr` 的进程拿不到跳蹲动作（维度被清零），
`--role ud` 的进程换不了道。所以两台雷达发同一套完整数据也不会互相抢动作。

## 二、只改 6 个变量，然后双击

在 `tools\run-dual.bat` 顶部找到这一段，按实际雷达接口改：

```bat
set PY=py -3

set LR_FROM=udp
set LR_ARG=--udp-port 8888

set UD_FROM=udp
set UD_ARG=--udp-port 8889

set LR_PORT=9001
set UD_PORT=9002
set HUB_PORT=8766
```

`LR_FROM / LR_ARG` 怎么填，取决于雷达往外吐数据的方式（**先问数据组**）：

| 雷达怎么出数据 | `*_FROM` | `*_ARG` |
|---|---|---|
| 往本机某个 UDP 端口发包（最常见） | `udp` | `--udp-port 8888` |
| 雷达开了 TCP 服务，我们去连 | `tcp` | `--tcp 192.168.1.50:9000` |
| 雷达主动连到本机端口推数据 | `tcp-listen` | `--listen-port 9100` |
| 雷达提供 HTTP 接口，定时轮询 | `http` | `--http http://192.168.1.50/api/target` |
| 厂商 SDK / 上位机命令行 | `exec` | `--exec "C:\vendor\radar_cli.exe --dev 1"` |

改完双击 `run-dual.bat`，会弹出三个黑窗口。

## 三、每个窗口里应该看到什么

### 窗口 1（RADAR-LR）

```
后台判定：开（分工 lr）—— 游戏只收 left/right/jump/slide 结果
  进道 0.36 / 回道 0.22 / 横向增益 1.00 / 换道冷却 120ms
输出 ws://0.0.0.0:9001
收到: {"x":-0.42,"confidence":0.9,...}
成帧: x=-0.4200 jump=0.00 crouch=0.00
动作: left(lane=0)
```

看到 `动作: left` / `动作: right` 就对了。**这个窗口出现 jump 或 slide 就是错的**。

### 窗口 2（RADAR-UD）

```
后台判定：开（分工 ud）
动作: jump(lane=1)
动作: slide(lane=1)
```

只会出现 `jump` / `slide`，不会出现 `left/right`。

### 窗口 3（RADAR-HUB）

```
LR 上游已连接 ws://127.0.0.1:9001
UD 上游已连接 ws://127.0.0.1:9002
输出 ws://0.0.0.0:8766
→ 游戏 jump（ud，lane=1）
运行中：转发动作 12 个，去重丢弃 0 个，在线客户端 1 个
```

## 四、开游戏

先起一个静态网页服务（只需一次，在仓库根目录执行）：

```bat
py -3 -m http.server 8099 --bind 127.0.0.1
```

浏览器打开：

```
http://127.0.0.1:8099/index.html?input=radar&judge=backend&radar=ws://127.0.0.1:8766
```

三个参数的作用：

| 参数 | 值 | 含义 |
|---|---|---|
| `input` | `radar` | 用雷达输入 |
| `judge` | `backend` | **关键**：判定在后台，游戏只收结果 |
| `radar` | `ws://127.0.0.1:8766` | 指向 hub，不是指向某一台雷达 |

> 跨机器时把 `radar` 换成 `ws://<跑后台那台机器的IP>:8766`，并确认防火墙放行。

## 五、验收（3 条，全过才算通）

1. **动作分工正确**：挡左右雷达，只有窗口 1 出动作；挡上下雷达，只有窗口 2 出动作。
2. **游戏有反应**：横向挥手能换道，原地跳能起跳，蹲下能滑铲。
3. **状态帧正常**：游戏调试面板里 `lr_ok` / `ud_ok` 都是 true，`x` 会跟着人动。

没雷达时先用 `run-dual-demo.bat` 跑一遍（纯假数据，10 秒一次跳/蹲），链路通再接真机。

## 六、出问题先看这里

| 现象 | 原因 | 处理 |
|---|---|---|
| 窗口 1/2 一直不打印「收到」 | 上游接口选错或端口不对 | 保持 `--print-sample`，先确认雷达到底往哪发；必要时 `--from exec` 起厂商 SDK |
| 有「收到」但没有「动作」 | 信号没到阈值，或字段名没对上 | 看窗口里的 `成帧:` 行，`x` / `jump` 是否在动；不动就调 `--map`、`--scale-x`、`--invert-x` |
| 游戏显示「上游未开 --judge」 | 某个 bridge 忘了加 `--judge` | 加上重启该进程 |
| 游戏连不上 / 一直「连接中」 | hub 没起，或端口不是 8766 | 看窗口 3 是否在跑；确认 URL 里的端口和 `HUB_PORT` 一致 |
| 动作重复触发两次 | 上游重发同一帧 | 已有去重，仍出现就调 `--jump-gap-ms` / `--slide-gap-ms` 或前端 `actionDedupMs` |
| 换道太灵敏 / 太迟钝 | 阈值不合适 | 调窗口 1 的 `--enter-th`（进道）、`--exit-th`（回道）、`--x-gain` |
| 跳完一直保持跳 | 上下雷达帧率低（1.92Hz），恢复瞬间补跳 | 已内置「掉线恢复首帧不判动作」；仍出现把 `--judge-stale-ms` 调到 900~1000 |
| 两路数值几乎一样 | 厂商 SDK 单例/独占，两个进程读到同一台 | 改用 `--from exec` 各自指定不同设备号，或改单进程双实例 |
| 端口被占用 | 上一次的窗口没关 | 关掉旧窗口，或改 `LR_PORT / UD_PORT / HUB_PORT` |

## 七、手感调参（只改启动参数，不用改代码）

| 参数 | 默认 | 管什么 | 加在哪个窗口 |
|---|---|---|---|
| `--enter-th` | 0.36 | 从中间甩到左右需要的横向量 | 窗口 1 |
| `--exit-th` | 0.22 | 从左右回到中间需要的量（滞后，防抖） | 窗口 1 |
| `--x-gain` | 1.0 | 横向灵敏度放大 | 窗口 1 |
| `--lane-cooldown-ms` | 120 | 两次换道最小间隔 | 窗口 1 |
| `--max-lane-step` | 1 | 单帧最多换几档 | 窗口 1 |
| `--judge-jump-th` | 0.5 | 起跳判定阈值 | 窗口 2 |
| `--judge-crouch-th` | 0.5 | 下蹲判定阈值 | 窗口 2 |
| `--jump-gap-ms` | 450 | 两次跳最小间隔 | 窗口 2 |
| `--slide-gap-ms` | 400 | 两次滑铲最小间隔 | 窗口 2 |
| `--judge-stale-ms` | 800 | 多久没帧算掉线（上下雷达要 > 520） | 窗口 2 |
| `--min-conf` | 0.3 | 低于此可信度的帧丢弃 | 窗口 1/2 |

改完只要重启对应窗口，游戏不用刷新。

## 八、想退回旧模式（游戏前端自己判定）

去掉 URL 里的 `judge=backend`，或用：

```
http://127.0.0.1:8099/index.html?input=radar&judge=client&radar=ws://127.0.0.1:9001
```

此时游戏会自己判定，`radar` 可以直接指向某一个 bridge（去掉 `--judge` 启动）。
两种模式不要混用：开了 `--judge` 的 bridge 只发动作帧，客户端模式收不到连续帧。

---

## 九、两条硬限制，提前说清楚

1. **后台合并不会提高帧率**。上下雷达实测 1.92Hz，慢的那一路仍是体感上限。
   后台判定只是让动作更稳、掉线不补跳，变不出没采到的动作。
2. **厂商 SDK 必须允许两个进程各抓一台**。如果 SDK 是单例 / 独占设备 / 固定本地端口，
   双开会串台（两路数值一样）。先用两个 `--print-sample` 进程手挡天线面验证，
   不行就退到「单进程双实例」。

---

## 十、和你熟悉的「5-推流到游戏.cmd」是什么关系

`radar-service\5-推流到游戏.cmd` 会自动识别两块板，起两个 `radar_live_ws.py` 进程，
分别出 `8766`（lr）和 `8767`（ud）。**"两个进程各读一台"这件事它已经做到了。**

差别在最后一步：它虽然内部已经用 `ActionRecognizer` 判出了左右/跳/蹲，
但发出去的是连续帧（`x / jump / crouch`），游戏前端还会再判一次。
所以它**本身还不是**「游戏只收结果」。

因此：

| 你的目标 | 怎么做 |
|---|---|
| 马上验证「游戏只收结果」 | 按本手册第二~四节走：`run-dual.bat` + hub，**不要**同时开 `5-推流` |
| 想复用官方脚本的自动识别板型 / 标定 | 需要先让 `radar_live_ws.py` 直接输出 action 帧，这一步还没做，找项目负责人确认 |

两条链路不要同时起来，会抢串口和 8766 端口。
