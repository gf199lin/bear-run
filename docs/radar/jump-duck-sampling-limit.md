# 2T4R 采样上限：跳这个动作在硬件上能不能采到

> 2026-11-02。回答一个具体问题：**2T4R 在纵向（俯仰）上，人腾空的那段时间能采到几帧？**
>
> 结论：**最多 1 帧，典型 0–1 帧，要 3 帧在物理上不可能。**
> 这不是代码或判据的问题，是帧率决定的采样上限。

## 1. 硬数字

| 项 | 值 | 来源 |
|---|---|---|
| 2T4R 帧周期 | **0.52084 s** | `seg_01.00.labels.jsonl` 的 `_meta.frame_period`（实测） |
| 2T4R 帧率 | **1.92 Hz** | 上式取倒数 |
| 1T2R 帧周期 | 0.1295 s（7.72 Hz） | AGENTS.md 事实基线 |

## 2. 腾空时间有多长

自由落体公式 `t = 2√(2h/g)`，取 g = 9.81：

| 跳高 | 腾空时间 | 除以 0.52084 | 能采到的帧 |
|---|---|---|---|
| 20 cm | 0.404 s | 0.78 个周期 | **0–1 帧** |
| 30 cm | 0.495 s | 0.95 个周期 | **0–1 帧** |
| 40 cm | 0.571 s | 1.10 个周期 | **1–2 帧** |
| 50 cm | 0.639 s | 1.23 个周期 | **1–2 帧** |

采到 N 帧的下限是腾空 ≥ (N−1)×帧周期：

| 想要 | 需要腾空 | 对应跳高 |
|---|---|---|
| 2 帧 | ≥ 0.521 s | ≥ 0.33 m |
| **3 帧** | **≥ 1.042 s** | **≥ 1.33 m** |

人类垂直跳（立定跳高）普通人在 0.3–0.5 m，专业运动员约 1.0–1.2 m。
**1.33 m 不属于可用范围** —— 所以"腾空段采满 3 帧"这条要求无法通过。

## 3. 整个跳动作也只有 2 帧

一次完整跳跃 ≈ 预蹲 0.3 s + 腾空 0.5 s + 落地缓冲 0.4 s ≈ **1.2 s**，
在 1.92 Hz 下约 **2 帧**。也就是说：

- 判据里 `up_frames = (1, 2)` 在 2T4R 上实际只有 **1**；
- `max_up_frames = 3` 等于**不限**（永远达不到 3）；
- 校准结果把 `up` 推到 3、`dn` 压到 1，正是这个上限的体现，不是调参失败。

## 4. 现有数据能证明什么、不能证明什么

对 `data/vertical` 的 7 个会话、34 个动作段逐帧统计（`pitch_seq`）：

| 指标 | 结果 |
|---|---|
| 每段帧数 | 固定约 **22 帧 = 11.5 s** |
| 段内 \|偏离\| ≥ 8° 的帧数 | 中位 11 帧 |
| 段内最长连续 ≥ 8° | 中位 4 帧 |
| 段内偏离标准差 | 中位 **8.7°** |

**注意这两条读法**：

1. 段长固定 22 帧、11.5 秒，说明这些"段"是**固定长度的采集窗口**，
   不是按动作起止切出来的。所以"段内有 11 帧偏离"**不等于**"一次跳采到 11 帧"，
   不能拿来反驳上面的采样上限。
2. 段内偏离标准差 8.7°，与动作幅度（8–18°）**同量级**。
   即使某一帧真落在腾空瞬间，信噪比也只有 1 左右，单帧不足以判定方向。

所以现有数据既不能证明"采到了腾空"，也不能证明"没采到"——
它只是在固定窗口里记录了混合了动作与噪声的俯仰序列。
真正要知道腾空帧长什么样，必须用**带真值时刻**的采集（提示音 + 帧号），
这正是 `tools/jumpduck_capture.py` 的设计。

## 5. 三条可行路径

### A. 提高 2T4R 帧率（改 chirp 配置）—— 当前采用

帧周期 = `ChirpsPerFrame × chirp 周期`。2T4R 的 chirp 周期实测 **8.138 ms**
（由 TDM 双 TX 交替 + 4 RX 数据量决定），所以只减 chirp 数即可提帧率：

| 目标帧率 | ChirpsPerFrame | FrameTimeUS | 帧周期 | 0.5 s 腾空采帧 | 速度分辨率 |
|---|---|---|---|---|---|
| 1.92 Hz（现状） | 64 | 520840 | 0.521 s | 0–1 | 0.0117 m/s |
| 3.85 Hz | 32 | 260420 | 0.260 s | 1–2 | 0.023 m/s |
| **7.68 Hz（目标）** | **16** | **130210** | **0.130 s** | **3–4** | 0.047 m/s |

**为什么选 16 而不是 24/32**：要 3 帧，帧周期必须 ≤ 0.5/3 ≈ 0.167 s；
16 chirps → 0.130 s 留有余量。32 chirps 只有 0.260 s，仍不够。

**为什么代价可以接受**：跳蹲判据用的是**俯仰相位差**，不依赖多普勒分辨率。
chirp 数减少只影响速度维（0.0117 → 0.047 m/s，左右换道判据用的是水平角，也不受影响），
代价主要是相干积累少 6 dB SNR —— 角度会更抖，需要用基线帧平滑抵消。

#### A-1 操作步骤

1. **打开 ONELAB 上位机的 `Radar_Config.ini`**，在 `[WAVE_INFO_0]`（或对应波形段）里
   找到并修改两个字段，**必须同比例改**：

   ```
   ChirpsPerFrame = 16
   FrameTimeUS    = 130210
   ```

   > ⚠ 只改 `FrameTimeUS` 不改 `ChirpsPerFrame`，会把 chirp 周期压到 2.03 ms，
   > ADC 采样窗口不足，数据会整片损坏。
   > 反过来只改 chirps 不改 FrameTimeUS，帧内会留下空转时间，帧率不会提升。

2. **下发配置**并确认雷达重新启动出流。

3. **让代码跟随**（三选一，推荐环境变量，全链路自动一致）：

   ```powershell
   # 当前 PowerShell 会话内所有工具都生效
   $env:RADAR_2T4R_CHIRPS = "16"
   ```

   或单次命令行覆盖：`python tools\jumpduck_ws.py --chirps 16`
   或永久改 `radar-pointcloud/radar_source.py` 的 `BOARD_PROFILES['2t4r']['chirps']`。

4. **实测验证**（这一步不能省，ini 改了不代表帧周期真的变了）：

   ```powershell
   python .deepworks\tmp\probe_frame.py COM4 8
   ```

   要看到：`chirp 索引: 16 个，范围 0..15`、`帧间隔中位 ≈0.130 s`、`1.87 Hz → 7.7 Hz`。
   如果 chirp 仍是 0..63 或帧间隔没变，说明配置没下发成功，回到第 2 步。

5. **重采数据 + 重校准**：

   ```powershell
   python tools\jumpduck_capture.py --port COM4 --out data\vertical\r16
   python tools\train_jumpduck.py --calibrate-prior --data data\vertical
   ```

   这时 `up_frames` 才可能真正落在 1–2 且数据里存在多帧上冲。

#### A-2 改完必须同步的地方

| 位置 | 改什么 | 不改的后果 |
|---|---|---|
| `Radar_Config.ini` | ChirpsPerFrame=16、FrameTimeUS=130210 | 帧率不变 |
| 环境变量 / profile | `RADAR_2T4R_CHIRPS=16` | 组帧要求 4×64 全满，**一帧都凑不齐** |
| 采集元数据 | 帧周期写进 `labels.json` | 真值时间轴错 4 倍 |
| `EXPECTED_SPEC.frame_rate_hz` | 仍写 5.0（下限），7.68 已满足 | 判据误报"采样不足" |

**当前状态**：代码已支持 `--chirps` / `RADAR_2T4R_CHIRPS`（默认仍 64，兼容现有板子）；
ini 尚未修改，等实测通过后再把 profile 默认值一次性改成 16。

### B. 换 1T2R 的多普勒（7.72 Hz）

腾空 0.4–0.5 s 可采 **3–4 帧**，帧率这一关能过。但有两个新问题：

1. **没有垂直角**，只能用多普勒/幅度间接判断（AGENTS.md 事实基线）；
2. **最大不模糊速度 ±1.53 m/s**。起跳速度 `v = √(2gh)`：
   跳 20 cm → 1.98 m/s，跳 30 cm → 2.43 m/s，**都会折叠**。
   只有跳高低于约 12 cm 才不模糊。

所以 1T2R 能采到腾空过程，但速度符号不可信；能否用能量/幅度特征区分跳蹲，
**未验证**，需要单独实验。

### C. 改动作定义（不改硬件）

2T4R 能可靠采到的是**持续 ≥1 s 的姿势**，不是 0.5 s 的瞬时动作。

- **蹲**：本来就是持续 2–3 s 的姿势 → 2T4R 可测（4–6 帧）。
- **跳**：改成"双臂上举 / 纵向挥手"这类**持续 1 s 以上**的纵向动作，
  5 Hz 下能采 3–5 帧，判据才立得住。

这条路改动最小，但改变了"跳"的交互语义，需要产品侧确认。

## 6. 对当前代码的影响

- `EXPECTED_SPEC` 已加入 `measured` 与 `viability` 字段，明确 2T4R 只有 1.92 Hz、
  不满足 5 Hz 要求。
- `jumpduck_ws.py` 启动时会打印期望形态；**在 2T4R 上跑 jump 判据应当被视为实验性**。
- 文档与汇报里不得把"跳"写成已验证能力（AGENTS.md 硬约束 5）。

## 7. 一句话给评审

> 跳是一个 0.5 秒的动作，2T4R 每 0.52 秒才出一帧，
> 采样点数量上就不够，与算法好坏无关。
> 要测跳必须先把帧率提上去（改 chirp）或把动作时长拉长，
> 否则这条路在第一步就不成立。
