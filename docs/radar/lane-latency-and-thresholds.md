# 左右识别：门限与延迟实测（2026-11-03）

数据：`data/lr3c`（16 段，LEFT 8 / RIGHT 8，1T2R，站位 1.0 m，中线 +9°，电脑侧 +35°~+90° 已排除）。
评估：`tools/lane_eval.py`（产线路径，`crit=xbase`）。

## 1. 门限扫描（固定 win 0.8 / confirm 3 / interval 0.5）

| 门限 L/R | 准确率 | 误报 |
|---|---|---|
| 0.14 / 0.18（旧默认） | 75.0% | 12 |
| **0.14 / 0.12（新默认）** | **87.5%** | **20** |
| 0.12 / 0.12 | 87.5% | 28 |
| 0.12 / 0.14 | 75.0% | 25 |
| 0.10 / 0.10 | 93.8% | 37（太吵） |

结论：RIGHT 门限 0.18 → **0.12**。已写入 `radar-pointcloud/radar_actions.py` L303。
（以上为 lr3b 扫描；lr3c 用新默认值实测 **93.8%（LEFT 8/8、RIGHT 7/8），误报 24**。）

## 2. 延迟扫描（lr3c）

| 配置 | 准确率 | 误报 | 延迟中位 |
|---|---|---|---|
| win 0.8 / confirm 3 / iv 0.5（默认） | 93.8% | 24 | **1.81 s** |
| win 0.4 / confirm 1 / iv 0.3 | 93.8% | 48 | 1.55 s |
| win 0.4 / confirm 1 / iv 0.3 / thr .20/.18 | 81.2% | 30 | 1.68 s |
| win 0.4 / confirm 1 / iv 0.3 / thr .24/.20 | 75.0% | 25 | 1.68 s |
| win 0.3 / confirm 2 / iv 0.3 / thr .20/.18 | 87.5% | 33 | 1.68 s |
| win 0.6 / confirm 2 / iv 0.4 | 93.8% | 39 | 1.68 s |
| win 0.5 / confirm 2 / iv 0.4 | 93.8% | 43 | 1.68 s |

两个反直觉结果：

1. **提高门限不会降延迟，反而更慢**（1.55 → 1.68）。门限越高，dev 需要积累得越久才越过它。
2. **所有组合都锁在 1.68 s（≈13 帧）**，只有默认的 0.8 s 窗口是 1.81 s（14 帧）。参数只值 1 帧。

## 3. 为什么延迟压不下去

标签显示每段时长 **2.59 s（20 帧）**，`t_start` 是提示时刻。事件落在 1.55–1.68 s，即**动作已经进行了一半多**。最快的一段 0.52 s 就触发了。

所以延迟的构成是：

```
人的反应时间（~0.3 s）
+ 横移 0.3 m 本身要的时间（~1.0 s）
+ dev 平滑需要动作过半才稳定（~0.3 s）
+ 7.7 Hz 采样再丢 1 帧（0.13 s）
≈ 1.7 s
```

这是**动作协议的物理下限，不是算法缺陷**。继续调 `xbase_win` / `confirm` / `min_interval` 只能换来 ±1 帧，代价是误报翻倍。

## 4. 结论与建议

- 采用默认的 win / confirm / min_interval，只把 RIGHT 门限降到 **0.12**。
  lr3c 实测：93.8%，误报 24，延迟 1.81 s。这是当前最优平衡点。
- **不要再靠调参压延迟。** 想让手感变好只有两条路：
  1. **改动作协议**：把「慢慢横移 0.3 m」换成「快速挥臂/踏步」——峰值在 0.3–0.4 s 就会出现，延迟可望进 1 s 内。这符合 `AGENTS.md` 的「动作触发」范式，也符合 7.7 Hz 的现实。
  2. **游戏侧吸收延迟**：障碍提前 2 s 可见 + 换道动画 0.3 s，让 1.7 s 的判定延迟不落在视觉关键帧上。
- 若要验证第 1 条，需新采一批「快速挥手」数据（同样 16 段），再跑本表对比。
