## 三、本次定位到的两个硬件级故障

### 3.1 距离带写死导致丢 48% 的帧

`radar-pointcloud/calib.json` 里 `band=[0.681, 1.363]`，只覆盖一个距离 bin。
1T2R 在 1.0 m 站位下实际有**两个** bin：

| bin | 距离 | 占据率 | 每帧点数 |
|---|---|---|---|
| bin1 | 1.022 m | 65% | 1.273 |
| bin2 | 1.703 m | 10% | 0.123 |

两者差一个距离分辨率（≈0.68 m）。写死低的那个会丢掉高的那个，
这是此前「检出率 47%」说法的来源。

**处理**：`LR_ARGS` 改为 `--band 0.5,1.9`，两个 bin 都覆盖。

### 3.2 `zero` 锁到墙导致整档数据饱和

`radar_live_ws.py` 启动后 `--zero-secs 3` 秒内取角度中位数作为零点。
如果这 3 秒内人还没到位，`zero` 会锁到视野里最强的静止反射体。

实测（2026-11-19 21:42，人不在位重启）：

```
zero = -25.40        锁到墙/显示器
x    -1.000 ~ -0.067  全程贴在最小值
```

人站 0° 附近时 `x = (0 − (−25.4)) / 20 = 1.27`，被 clamp 成 1，再乘
`--lr-flip` 的 −1，**从第一帧就饱和在 −1**。

人在位重启后恢复正常：

```
zero = -2.85
x    -0.620 ~ +0.289
```

**结论**：这是流程问题不是参数问题，`zero` 必须在人站好时锁定。

## 四、数据丢失的原因与修复

游戏侧 `Calibration.clear()` 旧实现删除的是**固定 KEY**，不区分玩家：

```js
localStorage.removeItem('bear-run:calib:v1');   // 不管现在是谁
```

校准失败走清理路径时会把别人的档一起抹掉。2026-11-19 21:37 的一次采集
因此丢失。

**处理**：改为按名字存档。

| KEY | 用途 |
|---|---|
| `bear-run:calib:<name>` | 每个玩家独立的档 |
| `bear-run:calib-bak:<name>` | 覆盖前自动备份 |
| `bear-run:calib:current` | 当前选中的玩家 |

旧 KEY 自动迁移成「默认」，已存在的数据不丢。

### 一个实用的判据

`track_az()` 在探测不到点时**返回上一次的角度**，`confidence` 仍是 0.9。
因此判「雷达有没有看到人」不能看 `az`，只能看点数 `n`（>0 才说明当帧真有目标）
和 `confidence` 档位（0.9 = 当帧有目标，0.75 = 丢帧保持）。

## 七、跳蹲板未启动的直接原因

`.deepworks/tmp/dual-radar-assign.json` 的 `roles` 只有 `COM5: lr` 与 `COM3: lr`，
**COM6 从未分配角色**，因此 8767 端口长期为空。与跳蹲算法无关。

同时 `COM5: lr` 是脏记录（COM5 已离线，插回会与 COM3 抢 lr）。

**处理**：改为 `{COM3: lr, COM6: ud}`。该文件位于 `.deepworks/tmp/`，按仓库规矩
不进 Git，换机器后需重做。
