# 双雷达接入游戏：四个动作的完整链路（2026-11-17）

> 本文记录「水平 + 竖直」两块 1T2R 同时接进《熊二快跑》的实现路径、判据来源与
> **已执行的验证**。凡未在真机双板同跑中复现的，一律标为「未验证」。

## 1. 链路

```
1T2R 横放 ──串口──> radar_live_ws.py --role lr --mode pos
                        判据：radar-pointcloud/radar_actions.py xbase + 现场零点
                        ws://127.0.0.1:8766  {x, confidence}
1T2R 竖放 ──串口──> radar_live_ws.py --role ud --jump-engine sm --jump-band 1,3
                        判据：tools/jumpduck_sm.py（径向速度状态机）
                        ws://127.0.0.1:8767  {jump, crouch, confidence}

两路 ──> dual-radar-kit/js/InputSource.js  DualRadarInputSource
            lr 通道只取 x -> left / right
            ud 通道只取 jump / crouch -> jump / slide
            ↓ GameEvent
         Game.handleAction -> Player.jump / Player.slide / 换道
```

角色分配由 `tools/dual_radar_manager.py` 负责（两块 1T2R 的 VID:PID 相同，只能按插入顺序
或手动下拉框区分），它同时托管 `dual-radar-kit/` 静态页面。

## 2. 判据来源（不是拍脑袋的阈值）

| 动作 | 判据 | 参数 | 依据 |
|---|---|---|---|
| 左 / 右 | 瞬时方位角 → 位置电平，游戏端滞回 | `enterThreshold 0.36` / `exitThreshold 0.22` | `dual-radar-kit/js/config.js` L471-474；M1 验收路径 |
| 跳 | 负径向速度段 1–2 帧后转正 | `v_t=0.15`、`nz_t=0.30`、`cooldown=8` 帧 | `tools/jumpduck_sm.py` L46 |
| 蹲 | 负径向速度段 ≥3 帧 | `nb_duck=3`、`quiet=6` | 同上 |

跳蹲参数来自 2026-11-13 四批采集（`data/jumpduck_battery/`），属**提案，待小组确认**。

两块板的固定摆法（采集时就是这个几何，现场必须一致）：

- **竖直板用 1T2R**：跳蹲判据是在 1T2R 竖放上采的，2T4R 的距离带与速度分辨率不同，不能直接套 `--jump-band 1,3`；
- 水平板：横放，人站正前方约 1 m；
- 竖直板：绕光轴转 90° 竖放，离地约 0.5 m，人站约 1.2 m；
- 都避开显示器/机箱那侧，否则最强点会被静止强反射抢走。

## 3. 本轮修的两个真问题

### 3.1 竖直帧被游戏整帧丢掉（会让跳蹲完全失效）

`radar_live_ws.py` 原来用「角度跟踪是否看到人」算置信度，看不到就给 `0.2`。
游戏端 `confidence < minConfidence(0.3)` 会直接 return，一帧都不进解码器。
竖直板本来就可能看不到人的躯干角，于是跳/蹲事件全部丢掉。

现在按角色分开算（`shape_frame()`，`dual-radar-kit/tools/radar_live_ws.py`）：

- 水平路：仍然用角度质量当置信度（看不到人就必须压低，否则乱换道）；
- 竖直路：判据是速度谱，与角度无关 —— 推流即 `0.85`，事件帧 `1.0`。

### 3.2 两套跳蹲判据互相打架

`--jump-engine sm` 时，`ActionRecognizer` 的 `JUMP/DUCK` 事件原先仍会叠加到同一帧。
那套判据在静息时误报率高（见 `docs/` 内相关记录），会和状态机抢动作。
现在状态机生效时直接跳过 legacy 的跳蹲事件，只保留左右/目标丢失事件。

## 5. 现场怎么用

1. 两块 1T2R 都插上；
2. 双击根目录 `启动-双雷达游戏.cmd`；
3. 页面「0. 雷达分配」确认 **插入序 1 = 水平、2 = 竖直**（反了点「交换水平 / 竖直」）；
4. 点「启动并回游戏主页面」→ 两路桥接起来 → 回到主菜单（不自动弹校准）；
   主菜单显示「雷达已连接 · 水平✓ 竖直✓ · 帧/秒 · 未校准（点「校准雷达动作」）」，确认两路都在推流后再点「开始游戏」。
5. **进游戏发现左右反了**：回联调台第 3 张卡片，点「左右镜像」——雷达的左右整体取反，
   水平桥接自动重启（约 1 秒），游戏页自动重连；再点一次翻回来。

### 左右镜像（2026-11-17）

同一套摆法，成像方向可能因为斜放 / 人站哪一侧而左右互换。以前只能改命令行参数，现场不好用，
所以做成联调台上的一个开关：

| 项 | 说明 |
|---|---|
| 按钮 | 联调台第 3 张卡片「① 左右方向对不对」下方，「左右镜像：关 / 开」 |
| 接口 | `POST /api/flip-lr`；不带参数 = 翻一次，`{"lr_flip":true\|false}` = 直接设定 |
| 实现 | `radar_live_ws.py --lr-flip`：`x` 整体取反（event 模式下 LEFT/RIGHT 也互换） |
| 持久化 | `.deepworks/tmp/dual-radar-assign.json` 的 `flags.lr_flip`，重开分配台仍记得 |
| 生效 | 水平桥接**重启一次**（响应里 `restarted: true`），游戏页 1～2 秒自动重连；没在跑时只记状态 |

为什么不在游戏端翻：左右是**感知层**的符号问题。在桥接翻，联调台的 x 曲线、校准的左右采样、
游戏里的换道三者才一致，不会出现「联调台说左、游戏往右」。

> 只翻水平那一路；竖直板的 jump / crouch 不受影响。

排错顺序：页面「桥接」列 → 「桥接日志」→ 第 2 张卡片的实时数值（x / jump / crouch 是否随动作变化）
→ 第 3 张卡片的两项自检。桥接日志在 `.deepworks/tmp/radar-lr.log` / `radar-ud.log`。

`radar_live_ws.py` 的竖直帧 `raw.sm` 里带 `v_r / nz / w`（径向速度、零多普勒外能量占比、谱宽），
静息时 `nz` 应 < 0.30；一直 ≥ 0.30 说明有人在动或板子被风扇/帘子扫到。

## 6. 端口与进程生命周期（2026-11-17）

现场最烦的一个坑：关掉页面/关掉 cmd 窗口后，`radar_live_ws.py` 并不会跟着退出
（Windows 不会级联杀子进程），8766 / 8767 一直挂着，下次点「启动」就报
「端口已被占用：先关掉旧的桥接」。修了两层：

**1. 桥接自己会退（`--idle-exit` 默认 60 s / `--lonely-exit` 默认 300 s）**

`Hub` 只在**真正完成 ws 握手**的连接上记账（裸 TCP 端口探测不算客户端，否则空闲计时永远被刷新）。
两条规则：

- `--idle-exit`：曾经连上过、现在全断开 → 连续 60 秒无人连 → 打印「客户端已全部断开 N 秒 → 自动退出并释放端口」
  → 删 pid 文件 → 退出；
- `--lonely-exit`：**启动后一直没有任何页面连上来**（跳转失败、页面根本没开）→ 300 秒后同样退出。
  没有这条时，一个没人用的桥接会把端口永久占住 —— 2026-11-17 实测踩到过（10:06 起的两个进程到 10:20 还活着）。

**2. 分配台启动前自动回收旧桥接（`reclaim_port`）**

每个桥接启动时把 pid 写进 `.deepworks/tmp/radar-<role>.pid`。分配台在 `stop_all()` / `start_all()`
里先看端口有没有人占：

- pid 文件记录的 pid 与 netstat 查到的监听者一致 → 确认是自己的旧桥接 → `taskkill /F` 并等端口释放；
- 没有 pid 文件（旧版本留下的）→ 用 `Get-CimInstance` 取命令行，含 `radar_live_ws` 才杀；
- 都不是 → 报错并给出 pid 与手动命令，不误杀别人的服务。

`/api/stop` 走同一条路径，所以页面「停止」也能清掉孤儿进程。

**8778 重复启动**：再双击 `.cmd` 时，如果 8778 上响应的 `/api/ping` 是本服务，直接打开页面并退出，
不再报"端口起不来"。根地址 `/` 302 到联调台，`/index.html` 才是游戏。

**验证**（`.deepworks/tmp/_port_reclaim/`）：

| 测试 | 结果 |
|---|---|
| 空闲自退：连上→断开（模拟关页面） | 5.7 s 退出，端口释放，pid 文件删除 |
| 无人连接自退：`--lonely-exit 5`，不连任何客户端 | 4.8 s 退出，端口释放，pid 文件删除；`--lonely-exit 0` 时 11 s 仍存活（对照） |
| 硬杀分配台 → 桥接成孤儿 → 再启动 | 日志「端口 8766 被旧桥接占用（pid 文件对上，pid 5244）→ 自动结束并回收」，新 pid 17364/10700，`/api/start` ok |
| `/api/stop` | 8766 / 8767 20 秒内释放，分配台退出后 8778 释放 |

> 测试注意：如果真实页面还开着并连着 8766，`--lonely-exit` 永远不会触发（那是正常客户端）。
> 做这类测试要换一个空闲端口（例如 8771），否则测的是「有客户端」场景。

## 7. 识别层两处调参（2026-11-17）

### 7.1 左右：按幅度分档（2026-11-17 三次调整）

根因不在雷达，在 `RadarDecoder` 的判定写法：站在边上（lane 0 / lane 2）那一支，
只要越过 `enterThreshold` 就直接跳到**对面**：

```js
} else if (this.lane === 0) {
  if (x >= R.enterThreshold) lane = 2;    // ← 一跳跨两根
```

而 `enterThreshold 0.36 × scaleDeg 20° ≈ 7.2°`，1 米外约 13 cm，手一动就到了。

**调整经过**（三次，前两次都踩了坑）：

1. 把「中间 → 边上」也套上 `bigStepThreshold 0.45`、冷却拉到 180 ms
   → 现场反馈**不灵敏**，挥到 45% 才换道，手感是「挥了手不动」。
   错在前提：**从中间出发最多只走一条道，根本不需要大幅门限**。
2. 门限改回 0.36 / 冷却 120 ms → 灵敏了，但暴露真问题：
   **小移动（< 12 cm）不触发，大移动一口气跨两根**，中间没有「只走一根」的档位。
3. 当前版本：把进道门降到 **0.22**（≈4.4°，1 m 处约 8 cm），
   并引入**「穿门」规则**（见下）解决「从边道拉到中间位置又被连判一格」的问题。

| 场景 | 门限 | 说明 |
|---|---|---|
| 中间(1) → 左/右（小幅） | `enterThreshold 0.22` | 约 8 cm 位移即可，且必须**从中间穿过去** |
| 中间(1) → 左/右（大幅跨步） | `bigStepThreshold 0.62` | 不受穿门限制（单帧限档会先压到中间，下一帧必须放过）|
| 一边(0/2) → 对面 | `bigStepThreshold 0.62` | 一次跨两根 |
| 一边(0/2) → 回中间 | `exitThreshold 0.12` | 收回近中线才回去（0.22→0.12 形成滞回）|
| 两次换道间隔 | `laneCooldownMs 120` | 一帧 129.5 ms，120 等于每帧都允许切 |

**「穿门」规则**（关键）：`lane === 1` 时，小幅换道还要求上一帧的 `|x|` 在门限以内：

```js
else if (x >= R.enterThreshold && prevX < R.enterThreshold) lane = 2;
```

没有这一条，人从左边拉到中间位置（x = 0.3）会被**连判两次**：
第一帧回中间，第二帧同一个 0.3 又满足「从中间进右道」，于是继续跨过去 ——
**小移动变成跨两根**，正是现场反馈的现象。

实测（headless 加载真实 `RR.RadarDecoder`，喂合成 x 序列，13/13 通过）：

| 起点 | x 序列 | 事件 | 落点 |
|---|---|---|---|
| 中间 | 0.4 ×4 | right | 2 |
| 中间 | 0.7 ×3 | right | 2 |
| 中间 | 0.5 ×3 | right | 2 |
| 中间 | 0.30 ×3 | right | 2（> 0.22 现在换道）|
| 中间 | 0.38 ×3 | right | 2 |
| 中间 | 0.24 ×3 | right | 2（刚过新门限）|
| 中间 | 0.20 ×3 | 无 | 1（< 0.22，防抖）|
| 中间(静止) | 0.3 ×3 | right | 2（从 0 穿上来）|
| 左边(0) | 0.3 ×3 | right | 1（**拉到中间就停住，不跨两根**）|
| 左边(0) | 0.3 ×2 → 0.5 ×2 | right,right | 2（中间停一帧再继续往右，不卡死）|
| 左边(0) | 0.0 ×3 | right | 1（拉回正中）|
| 左边(0) | 0.7 ×5 | right,right | 2（跨两根）|
| 右边(2) | 0.05 ×3 | left | 1 |

**已知取舍**：`bigStepThreshold` 只挡**单帧大甩**。人从最左一路拉到最右
（x 0 → 0.4 → 0.5）会先回中间、下一帧再进右道，两帧走完两根 —— 这是灵敏度的代价，接受。

改的三个文件必须同步：`js/config.js`、`js/InputSource.js`、`index.html`（打包产物）。

### 7.2 跳/蹲：负段后先观望 2 帧，85.4% → 93.8%

**基线**（`tools/jumpduck_sm.py`，6 批 96 样本）：判对 82/96 = 85.4%，
其中跳 35/48、蹲 47/48 —— 问题全在跳。

**漏在哪**：13 个漏检里 5~6 个是 `jump_l`（大跳）被判成 **duck**。
大跳落地反冲的负速度段有 4~8 帧，而状态机「负段凑够 `nb_duck=3` 帧就立刻判蹲」，
反冲还没转正就已经报了蹲。

**试过但不采用的两条**：

- **谱宽改判**（`doppler_width`，跳 0.308 / 蹲 0.202）：整段平均可分（跳 0.345+，蹲 ≤0.288），
  但**事件时刻**两类完全重叠（0.15~0.57），要等整段就得多等 ~400 ms，实时不划算；
- **早报**（活跃 2~3 帧就判）：判对率反而降到 65.6%。

**波形形态**（用户提的「周期内有几个波」）确实是分开的，只是不适合当实时门限：

- 蹲 = 双峰：高段 → **静默 5~6 帧** → 起身高段；
- 跳 = 单峰：负段后**立刻转正**（上冲/落地反弹），中间没有长静默。

**最终做法**：保留速度状态机，只把「凑够负段就判蹲」改成**先观望**：

```
NEG 负段 nb >= nb_duck
   └─ defer_duck > 0 → 压住 2 帧：
        期间 v > +v_t（转正）→ JUMP
        2 帧后仍未转正        → DUCK
```

对应参数 `--defer-duck`（默认 2）。离线结果：

| 方案 | 判对 | 跳 | 蹲 |
|---|---|---|---|
| 基线 defer=0 | 82/96 = 85.4% | 35/48 | 47/48 |
| 观望 1 帧 | 84/96 = 87.5% | 37/48 | 47/48 |
| **观望 2 帧** | **90/96 = 93.8%** | **44/48** | 46/48 |
| 观望 3 帧 | 89/96 = 92.7% | 45/48 | 44/48 |

代价：蹲多等 2 帧（+259 ms），跳的延迟不变（跳是「转正」触发，不走观望分支）。

**接入**：`radar_live_ws.py --jump-engine fusion --defer-duck 2`；
`tools/dual_radar_manager.py` 的 `UD_ARGS` 已带上，联调台点「启动」即生效。
离线复算：`python tools/jumpduck_fusion.py "data/jumpduck_battery/2026*"`。

> 阈值与参数均为本批 96 样本的提案，待更多样本确认。

### 7.3 跳/蹲：拆成「蹲多深」和「跳多高」两个幅度门（2026-11-17 三次调整）

现场反馈两条**相反**的问题：

- 起跳前的小蓄力（向下、幅度小）就被判成**蹲**；
- 真跳要幅度很大才触发，**跳不灵**。

根因：原状态机**只有速度方向和帧数，没有幅度维度**，`v_t = 0.13` 一个门限同时管跳和蹲。

**改成三个门**：

| 参数 | 管什么 | 取值 |
|---|---|---|
| `v_t` | 进负段（先看见动作） | 0.13 |
| `nz_t` | 单帧动作门：能量占比不到就整帧丢弃 | **0.20**（原 0.28）|
| `v_duck` | 判蹲：负段最深要到多少（EMA 后） | **0.35** |
| `v_jump` | 判跳：正速度峰值要多高（**原始值，不经 EMA**） | **0.32** |

`nz_t` 从 0.28 降到 0.20：现场反馈「跳不够灵敏」，而离线 46/46 已满分，
说明瓶颈不在判定阈值，在**帧被丢得太多** —— 样本整段平均 `nz_share` 只有
0.12~0.25（jump_k 0.117、jump_m 0.141），0.28 会把大量弱动作帧整帧挡在状态机外。
放宽到 0.20 后离线指标不变（跳 46/46、蹲 22/22 + 12/14、静息 4/4 无误报），
但现场弱动作能进来的帧明显变多。这是「离线测不出、只能现场验」的改动。

关键是两个门看**不同的物理量**：蓄力向下只有 0.2 左右，够不到 `v_duck`；
真跳正峰有 0.5，轻松越过 `v_jump`。跳改用原始峰值，是因为
`EMA(alpha=0.5)` 会把尖峰削掉一半，轻跳直接漏掉 —— 这是「跳要很大幅度」的第二个根因。

**实测**（`data/jumpduck_battery`：10 浅蹲 / 22 中蹲 / 14 全蹲 / 46 跳）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 小蹲误报成蹲 | 6/10 | **1/10** |
| 中蹲检出 | 21/22 | **22/22** |
| 全蹲检出 | 12/14 | 12/14 |
| 跳检出 | 45/46 | **46/46** |
| 跳延迟（中位） | 561 ms | **388 ms** |
| 静息误报 | 2/4 | **0/4** |

扫参依据：`v_jump` 0.35 → 跳 43/46；0.32 → 46/46；0.30 → 46/46 但全蹲掉到 11/14；
0.28 → 浅蹲误报跳升到 6/10。取 0.32。

**谱宽（`doppler_width`）为什么没进实时判据** —— 本轮重新用数据验证过：

| 类别 | 整段峰值−基线 | **事件后 1~2 帧** |
|---|---|---|
| 跳（小/中/大/缺上冲） | 0.305 / 0.661 / 0.903 / 0.472 | 0.234 / **0.249** / 0.289 / 0.261 |
| 蹲（浅/中/全） | 0.171 / 0.283 / 0.281 | 0.107 / **0.252** / 0.265 |

整段看确实可分（跳 ≥ 0.30，蹲 ≤ 0.28），但**事件后头两帧完全重叠**（跳 0.249 vs 蹲 0.252），
而谱宽峰值要到事件后 7~15 帧（0.9~1.9 s）才出现 —— 那时角色已经蹲下或跳完了。
所以保留为诊断字段（`USE_WIDTH = False`），不做实时改判。

实现位置：参数在 `tools/jumpduck_fusion.py`（`V_JUMP` / `V_DUCK`），
判定在 `tools/jumpduck_sm.py` 的 `NEG` 分支（追踪 `vneg` / `vpos`，
判蹲要 `abs(vneg) >= v_duck`，判跳要 `vpos >= v_jump`）。

> 上述数字来自离线回放，现场手感仍需人站实测确认。
