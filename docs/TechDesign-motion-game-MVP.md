## 2. 架构总览（分层，最小设计）

```
┌─────────────────────────────────────────────────────────────┐
│  L4 表现层 (pygame)        游戏画面 / HUD / 音效 / 结算界面     │
├─────────────────────────────────────────────────────────────┤
│  L3 游戏逻辑层 (game_core)  跑酷状态机 / 计分 / 命数 / 难度曲线  │
├─────────────────────────────────────────────────────────────┤
│  L2 状态识别层 (state_engine) 方位角分区 / 动作触发 / 去抖滞回   │
│                          [可选] jump_duck 子模块（验证门控制）   │
├─────────────────────────────────────────────────────────────┤
│  L1 数据层 (data_api)      协议解析 / 目标提取 / 录制回放       │
├─────────────────────────────────────────────────────────────┤
│  L0 链路层 (radar_link)   串口打开/关闭 / 读线程 / 帧重同步      │
└─────────────────────────────────────────────────────────────┘
          ▲                                    ▲
          │ 真实雷达 (DEV202H, CP2102)          │ 模拟器 (simulator)
          └────────────────────────────────────┘
```

**关键设计决定**：L0~L2 对上层**只暴露一个事件流接口**，真实雷达与模拟器**实现同一接口**（策略模式）。这样「游戏线不等雷达」（小组方案的核心策略）在架构上被强制保证。

## 3. 组件与职责

| 层 | 模块 | 职责 | 负责人 |
|---|---|---|---|
| L0 | `radar_link.py` | 串口枚举/打开（CP2102，921600）、读线程、帧头同步、异常重连、优雅关闭 | A+B |
| L1 | `data_api.py` | 二进制帧 → `RadarFrame`；目标提取（距离/方位角/速度/能量）；滑动窗口滤波；录制/回放 | B |
| L1 | `recorder.py` | 原始帧落盘（`.npz`/二进制）+ 时间戳；回放时按原时间轴推送 | B |
| L2 | `state_engine.py` | 方位角 → 扇区；**动作触发判定**（进入/离开扇区沿）；去抖（滞回 + 最小切换间隔）；输出离散事件 | B |
| L2 | `jump_duck.py` | **条件模块**：跳/蹲识别（验证门通过后启用） | A+B |
| L3 | `game_core.py` | 跑酷逻辑：跑道/障碍生成、碰撞、命数、距离计分、速度曲线、暂停 | C |
| L4 | `render.py` / `ui.py` | 画面渲染、HUD、音效、开始/结算界面、校准提示 | C |
| 工具 | `debug_view.py` | **独立离线工具**：pyqtgraph 实时/回放查看距离-多普勒与角度（不参与游戏运行） | B |
| 工具 | `simulator.py` | 假数据源：脚本化场景（球快/人乱动/人走开）+ 录制回放 | B+C |
| 支撑 | `config.py` / `logging_.py` | 参数集中管理；结构化日志（含状态判定轨迹，供验收取证） | C |

## 4. 接口契约（必须先冻结，M0 阶段确认）

### 4.1 输入帧

```python
@dataclass(frozen=True)
class RadarFrame:
    t_ms: int          # 单调时间戳（毫秒）
    targets: tuple[Target, ...]

@dataclass(frozen=True)
class Target:
    range_m: float     # 距离（米）
    angle_deg: float   # 水平方位角（度，右正左负）
    speed_mps: float   # 径向速度（米/秒，正=远离）
    energy: float      # 归一化能量
```

> **待确认（B，M0）**：`demo_1T2R` 实际输出的字段是否包含以上四项。若仅有点云/FFT 矩阵，则 `data_api` 需自行提取峰值目标（这是 B 在 D3–D4 的关键工作）。**契约在 M0 结束前冻结，冻结后不再变更。**

### 4.2 事件流（L2 → L3，唯一耦合点）

```python
class Event(Enum):
    LANE_LEFT   = auto()   # 左移一次
    LANE_RIGHT  = auto()   # 右移一次
    JUMP        = auto()   # 跳（条件性）
    DUCK        = auto()   # 蹲（条件性）
    CALIBRATED  = auto()   # 校准完成
    TARGET_LOST = auto()   # 目标丢失（>2s）
    TARGET_BACK = auto()   # 目标恢复

@dataclass(frozen=True)
class GameEvent:
    kind: Event
    t_ms: int
    confidence: float = 1.0
```

**模拟器与真实雷达都产出 `GameEvent`** → 游戏层完全不感知数据来源。

## 5. 关键算法与参数

### 5.1 方位角 → 扇区（左/中/右）

```
扇区划分（可配）: LEFT: angle < -15° ｜ CENTER: -15° ~ +15° ｜ RIGHT: angle > +15°
滞回阈值:        进入扇区需超过 ±15°，离开需回到 ±10° 以内（避免边界抖动）
```

### 5.2 动作触发换道（小组已确认的范式）

```
规则：以"进入扇区沿"作为触发，而非"当前所在扇区"
  CENTER → LEFT  触发 LANE_LEFT
  CENTER → RIGHT 触发 LANE_RIGHT
  LEFT   → CENTER 不触发（回到中立位，为下一次动作预备）
约束：最小切换间隔 ≥ 400 ms（对应约 3 帧 @7.7Hz，抑制抖动导致的连跳）
     判定期望：连续 2 帧落在目标扇区才提交事件（抗单帧噪声）
```

**设计理由**：7.7 Hz 下若用"当前位置映射"，玩家需持续保持站位；而"触发式"只需一次移动即可换道，与低帧率天然兼容（见 research §4.3）。

### 5.3 校准（F3）

```
采集：玩家站在正前方 3 s（约 23 帧）
得到：angle_bias（方位角零点）、energy_baseline（能量基线）、range_ref（参考距离）
成功判据：3 s 内 ≥ 80% 帧检测到稳定目标（能量与距离方差低于阈值）
失败处理：提示"请站到雷达正前方"并重试；连续 3 次失败 → 提示检查设备，可切模拟器
```

### 5.4 跳/蹲（条件模块，验证门控制）

按 research §4.2 的结论，**本模块默认不启用**。若 T0/T1 通过，实现路径为：

```
输入：滑动窗口（约 8 帧 ≈ 1 s）内的多普勒谱统计量
特征：多普勒正/负速度能量比、谱宽、能量质心距离趋势
判定：阈值规则（优先）→ 可分性不足时再考虑轻量分类器
约束：v_max ≈ ±1.53 m/s，超限样本需标注并单独分析（速度模糊）
决策点：T2（不通过 → 延至 2T4R）
```

### 5.5 难度曲线（F4，先砍项）

```
速度 = base_speed + k × floor(distance / step)
上限: 不超过 base_speed × 1.6（保证低帧率下仍可反应）
```

## 6. 数据流

```
[DEV202H] --UART 921600--> [radar_link] --raw frames--> [data_api]
                                                            │
                                          ┌─────────────────┴──────────────┐
                                          ▼                                ▼
                                   [recorder] (落盘)                 [state_engine]
                                                                           │
                                                                           ▼
                                                                    GameEvent 流
                                                                           │
   [simulator] ──────────── GameEvent 流 ──────────────────────────────────┤
                                                                           ▼
                                                                     [game_core]
                                                                           │
                                                                        [render]
```

**切换方式**：启动参数或运行时热键（`F2`）在「真实雷达 / 模拟器回放 / 模拟器脚本」间切换——**热键必须存在**，因为现场演示翻车时要在 1 秒内切换（F5 的核心价值）。

## 7. 失败行为与降级

| 失败 | 检测方式 | 行为 |
|---|---|---|
| 串口打不开 | 打开异常 | 提示 + 自动进入模拟器模式（不退出程序） |
| 运行中串口断开 | 读线程异常/超时 | 游戏自动暂停 + 提示；尝试重连（3 次，间隔 1 s） |
| 目标丢失 > 2 s | 连续无有效目标 | 游戏暂停（不扣命），恢复后继续（AC-6） |
| 数据抖动剧烈 | 状态频繁跳变 | 滞回 + 最小间隔抑制；日志记录以便调参 |
| 校准失败 | 判据不满足 | 引导重试（最多 3 次）→ 建议切模拟器 |
| 游戏帧率不足 | 帧率 < 30 FPS | 降低特效（去掉粒子/阴影），保逻辑帧率 |

**原则**：**任何设备问题都不得导致演示中断**——模拟器兜底是 P1 需求，不是可选项。

## 8. 部署与运行

```
运行环境: Windows 10/11 + Python 3.11+
依赖:     pyserial, numpy, pygame           (运行时)
          PySide6, pyqtgraph                (仅调试工具，可选装)
硬件:     DEV202H + CP2102（CP210x 官方驱动）+ ONELAB v1.5.4.1（仅训练/验证时使用）
启动:     python -m motion_game            # 默认尝试真实雷达，失败则进入模拟器
          python -m motion_game --sim      # 强制模拟器（彩排/兜底）
          python -m tools.debug_view       # 离线数据查看工具
```

**注意（来自 research R8）**：小组原方案写的是「装 FTDI 驱动」，**实测为 CP2102**，请以 CP210x 驱动为准，避免在 D2 步骤上浪费时间。

**安全边界**：本项目所有操作均为**本地**——不联网发送数据、不写生产环境、不涉及账号与支付。录制数据仅存本地（`C:\RadarData` 或项目 `data/`），且为**不含图像的人体雷达数据**；对外分享前需按课程保密要求确认。

## 10. 取舍记录（Tradeoffs）

| # | 取舍 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| T1 | 数据通道 | 官方 Python demo 自解析（主）+ `algorithm_gr` 探路（辅） | 可控性 + 快速验证兼得 | B 需自行解析协议 |
| T2 | 游戏框架 | pygame（游戏）+ PySide6/pyqtgraph（仅调试工具） | 避免调试 UI 与游戏循环耦合 | 需维护两套依赖 |
| T3 | 状态判定 | 规则法（阈值+滞回）优先 | 可解释、可调参、易验收 | 极端场景鲁棒性弱于学习法 |
| T4 | 交互范式 | 动作触发换道（非位置映射） | 与 7.7 Hz 低帧率天然兼容 | 玩家需理解"移动一次切一道" |
| T5 | 跳/蹲 | **不承诺**，走验证门 | 1T2R 无仰角通道，风险高 | 可能损失 2 个玩法动作 |
| T6 | 兜底 | 模拟器与真实雷达同接口、热键实时切换 | 现场演示零中断 | 需额外实现与维护模拟器 |
| T7 | 算法复杂度 | 不使用深度学习 | 数据量不足、时间两周、需可解释验收 | 上限受限（可接受） |

- **App**：毫米波雷达体感跑酷游戏（motion-game），Python 桌面单机
