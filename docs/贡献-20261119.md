## 一、定位到的两个真实故障

### 1.1 距离带写死导致丢 48% 的帧

`radar-pointcloud/calib.json` 里 `band=[0.681, 1.363]`，只覆盖一个距离 bin。

1T2R 在 1.0 m 站位下实际有**两个** bin：

| bin | 距离 | 占据率 | 每帧点数 |
|---|---|---|---|
| bin1 | 1.022 m | 65% | 1.273 |
| bin2 | 1.703 m | 10% | 0.123 |

两个 bin 正好差一个距离分辨率（≈0.68 m）。写死低的那一个会丢掉高的那个，
这就是历史记录里「检出率 47%、RIGHT 只剩 31 帧」的来源。

**处理**：`tools/dual_radar_manager.py` 的 `LR_ARGS` 改为 `--band 0.5,1.9`，
两个 bin 都覆盖。

### 1.2 `zero` 锁到墙，导致整档数据饱和

`radar_live_ws.py` 在启动后 `--zero-secs 3` 秒内取角度中位数作为零点。
如果这 3 秒内人还没站到位，`zero` 会锁到视野里最强的静止反射体上。

本机实测（2026-11-19 21:42）：

```
zero = -25.40        墙/显示器
az   -3.37 / -5.20 / -21.59   人和墙在抢
x    -1.000 ~ -0.067          全程贴在最小值
```

人站在 0° 附近时，`x = (0 − (−25.4)) / 20 = 1.27`，被 clamp 成 1，再乘
`--lr-flip` 的 −1，**从第一帧就饱和在 −1**。后续无论怎样校准，都只是在
饱和值之间做统计，`x0`/`aL`/`aR` 全是垃圾。

人在位时重启后恢复正常：

```
zero = -2.85
x    -0.620 ~ +0.289
```

**处理**：这是流程问题不是参数问题。`zero` 必须在人站好时锁定。

## 二、数据丢失的原因与修复

`bear-run-new/index.html` 旧版 `Calibration.clear()` 删除的是**固定 KEY**，
不区分当前玩家：

```js
localStorage.removeItem('bear-run:calib:v1');   // 不管现在是谁
```

一旦校准失败走清理路径，别人的档会被一起抹掉。2026-11-19 21:37 的一次
采集就是因此丢失的。

**处理**：改为按名字存档。

| KEY | 用途 |
|---|---|
| `bear-run:calib:<name>` | 每个玩家独立的档 |
| `bear-run:calib-bak:<name>` | 覆盖前自动备份 |
| `bear-run:calib:current` | 当前选中的玩家 |

旧 KEY 自动迁移成「默认」，已存在的数据不丢。

### `radar_selftest.py` 用到的一个判据

`track_az()` 在探测不到点时**返回上一次的角度**，`confidence` 仍是 0.9。
所以判「雷达有没有看到人」不能看 `az`，只能看：

- 点数 `n`（> 0 才说明这一帧真有目标）
- `confidence` 档位（0.9 = 当帧有目标，0.75 = 丢帧保持）

## 四点五、后续排查补充（同日 21:5x~22:0x）

### 4.5.1 跳蹲板一直起不来：COM6 从未分配过角色

`.deepworks/tmp/dual-radar-assign.json` 内容：

```json
"roles": { "COM5": "lr", "COM3": "lr" }
```

COM6 不在 `roles` 里，`seen` 里虽然有它的插拔记录，但没有角色就永远不会被启动。
这是 8767 端口长期空的直接原因，与跳蹲算法无关。

同时 `COM5: lr` 是一条脏记录：COM5 已离线，插回来会和 COM3 抢 lr 角色。

**处理**：

```json
"roles": { "COM3": "lr", "COM6": "ud" }
```

改完 `--port COM6 --role ud --ws-port 8767` 正常起，两块板都是 7.7 Hz。

该文件在 `.deepworks/tmp/` 下，按仓库规矩不进 Git，因此**这条修复不会被版本控制保留**，
换机器或清理 tmp 后需要重做。

### 4.5.2 「11/17 那位同学很准」的真相：其实没有校准

回溯 11/17 存档 `v-1117-verified` 的配置：

```
xGain: 1        ← 正好等于 js/config.js 的默认值
```

也就是说**当时没有用任何校准档，跑的是默认参数**。之所以能准确左右换道，靠的是：

1. `zero` 在启动时锁在了他站立的位置
2. 他站在 `zero` 上左右移动，偏移量直接落进默认门限（0.22）

**推论**：`x0=0 / xGain=1 / sign=1` 这套默认值本身没有问题，
出问题的永远是 `zero` 锁在哪。这一点决定了采集方案应该怎么设计——
不需要精密的幅度标定，只需要保证 `zero` 锁到人。

### 4.5.3 雷达波束朝向实测与历史记录不符

| 来源 | 有效方位区 |
|---|---|
| 11/03 记录（`docs/center-line-45.md` 等） | +9°（人站这一侧） |
| 11/19 空场与在场实测 | −27.5° ~ −30°（峰值），**+5° 以上 0 帧** |

两者相差约 35°。空场实测细节（无人时的回波分布）：

```
zero        = -28.2
有回波范围   = -35° ~ -10°，峰值 -30 ~ -25
+5° 以上    = 0 帧
n > 0 占比   = 17%，且最多 3 点
移开遮挡物后 = 无变化（-27.5°，42 帧）
```

移开遮挡物无变化，说明不是可移动障碍物，而是**墙或波束本身指向那边**。

**结论**：板子被转过。要么转回去对准人，要么让人站到 −27° 那一侧。
这个问题不解决，任何采集方案都会得到低质量数据。
