# 2T4R 帧率上限：卡在 UART 带宽，不是算法

- 日期：**2026-11-03**（正文） / **2026-11-05**（§9 复验）
- 状态：**已复验并修正**。§3 的「UART 带宽是硬约束」在 130 ms 配置下**不成立**：
  实测只要 70 kB/s（占 1.5 Mbps 的 47%），`Chirp NOT complete` 来自每帧只出 32/64 个 chirp。
  3 Mbps 已试，芯片接受命令但不出流。详见 §9。
- 关联：`docs/jump-duck-sampling-limit.md`（1.92 Hz 采样上限）、`docs/jump-duck-recognizer.md`

> 本文只记录**当天实测到的数字和日志证据**。任何未执行的步骤都标为「计划」，不得写成结果。

---

## 1. 目标

把 2T4R 的帧率从 **1.92 Hz** 提到 **≈7.5 Hz**，让「跳」的腾空段能采到 3 帧以上。
原有依据：`jump-duck-sampling-limit.md` 证明 1.92 Hz 下腾空只能采 0–1 帧，判据不成立。

---

## 2. 四次实测（全部来自 ONELAB 日志与串口实测）

| # | 配置 | 帧周期 | 需要的数据率 | 实测结果 |
|---|---|---|---|---|
| 1 | 64 chirp / T3 8000（基线） | 520.840 ms | 65 KB/s | ✅ 完整，491.67 包/s、65.3 kB/s |
| 2 | 64 chirp / T3 1900 / bins 16 | 130.440 ms | ≈130 KB/s | ❌ `Chirp NOT complete[31]`，每帧都报 |
| 3 | 32 chirp / T3 3900 | 131.72 ms | ≈129 KB/s | ❌ `Chirp NOT complete[12]` |
| 4 | 16 chirp / T3 8000 | 133.960 ms | 61 KB/s | ❌ `Chirp NOT complete[13]` |

补充现象：

- 第 2 组在 ONELAB 界面里已生效（距离范围 5.63 → **2.8 m**、分辨率保持 **17.6 cm**），
  但界面显示 `传输速率 68.600 KB/s`、`Frame 0`、波形平线、`距离门 -1`。
- 第 2 组同时出现 `OpenCmdMode: CMDID(0x00FF) failed with:A001`、`SetRxChannelBit: 0x0020 failed with:0FA8`。

---

## 3. 判断

**UART 1.5 Mbps（≈146 KB/s 实际吞吐）是硬约束。**

> **2026-11-05 修正**：本节按「32 bin / 4 RX」估算每帧 34 kB，但第 2 组实际是
> **16 bin（每帧 72 B）**，数据率只有 70 kB/s，占用 47%。带宽不是瓶颈，
> 见 §9 的实测与结论。以下原始推理保留作记录，不再作为当前结论。

一帧 64 chirp 约 34 kB。帧周期压到 130 ms 时，需要 260 KB/s，
超过串口能力 → 芯片还没把一帧塞完，下一帧就开始了 → 帧永远残缺。

只有 520 ms 帧周期（65 KB/s，占 45% 带宽）能完整传完。
**这解释了为什么「减 chirp」和「减 bins」都没用**：第 4 组只用到 61 KB/s 仍失败，
说明 16/32 chirp 的失败还叠加了另一个原因——帧内 chirp 计数寄存器与实际 chirp 数不一致（见 §4）。

## 4. 定位到的 chirp 相关寄存器（副产品）

对比「64 chirp」与「16 chirp」两份 ONELAB 下发日志，全量 140 条寄存器中只有 **3 处**变化：

| 地址 | 64 chirp | 16 chirp | 推测含义 |
|---|---|---|---|
| `0x600050E8` | `0xC000003F` (63) | `0xC000000F` (15) | 帧内 chirp 数 − 1 |
| `0x600050C4` | `0x1F1F0001` | `0x1F070001` | 每 TX chirp 数 − 1（31 → 7） |
| `0x600050F8` | `0x8000001F` | `0x80000007` | 同上（31 → 7） |

另有 `0x600050E4 = 31`、`0x600050F4 = 31` **未随 chirp 数变化**。
手工把它们改成 7 后，芯片从「0 字节」变成「5 kB/s 乱流」——说明方向相关，但取值不对。
**这组寄存器还没有定论，不要再盲改。**

## 5. 未完成：下次要做的第一件事

> **已于 2026-11-05 执行，结论见 §9。** 3 Mbps 不生效；真正的瓶颈不是波特率。

**提高串口波特率到 3000000（3 Mbps）。**

理由：2T4R 的 USB-UART 是 FTDI（COM4 在设备管理器里显示 `USB Serial Port`），
FT232 支持 3 Mbps。带宽翻倍后 ≈292 KB/s，当前配置需要 ≈130 KB/s，占 44%，有富余。

步骤（在 ONELAB 寄存器配置界面）：

1. 确认 `ChirpsPerFrame = 64`、`T3 = 1900`、`FFT输出列 = 16`、`FFT输出行 = 64`
   （即 `Frame 周期 130.440 ms`）
2. **UART 波特率 `1500000` → `3000000`**（若下拉无此选项，记录最高可选值，重新算帧周期）
3. 点「生成应用配置」→ 回主程序连接设备
4. 看是否仍有 `Chirp NOT complete`；同时看 `PC平均接收速度` 是否 ≈130 KB/s

判据：

- 日志无 `Chirp NOT complete` + `Frame` 递增 + 波形有起伏 → 成功，进入采集
- 仍报 → **2T4R 提帧率这条路判死**，转 §6

## 6. 如果 3 Mbps 也失败

2T4R 在 7.5 Hz 上做不出完整帧，结论成立且可写进报告：
**这块板的串口带宽撑不起跳所需的采样率，与算法无关。**

转向「持续纵向动作」方案：

- 把「跳」定义成**持续 ≥1 s 的纵向动作**（双臂上举 / 起立），1.92 Hz 下能采 4–6 帧；
- 「蹲」本身时长 2–3 s，1.92 Hz 已经够；
- 代价是交互语义变化，需要产品侧确认（AGENTS.md 硬约束 5 仍适用：T2 决策前不得写进「已实现」）。

## 9. 2026-11-05 复验：带宽不是瓶颈，3 Mbps 不生效

### 9.1 §5 那一步做了没有

**没有。** 11/03 的 ONELAB 日志里 7 次 `SetUartBaudrate` 全部是 `0x16E360`（1500000），
3 Mbps 一次未试。截图里的参数也仍是 1500000 + 130.440 ms。

### 9.2 复验方法（可复现）

1. 从 11/03 日志 `LogFile_2026_11_03_12_00_02.txt` 的 12:10:35 会话提取完整下发序列：
   31 帧 / 298 条寄存器（`.deepworks/tmp/extract_130ms.py` → `boot_seq_2t4r_130ms.json`，不入库）。
2. 用 `tools/uart_baud_probe.py` 重放配置并抓原始字节。
3. 解析：帧长随 bin 数变化（`帧长 = 8 + 4 × bins`；32 bin→136 B，16 bin→72 B）。

### 9.3 实测（同一块板，COM4，1.5 Mbps）

| 项 | 130 ms 配置 | 520.84 ms 基线 |
|---|---|---|
| 帧长 | **72 B（16 bin）** | 136 B（32 bin） |
| 数据率 | **70.2 kB/s** | 66.4 kB/s |
| 1.5 Mbps 占用 | **47%** | 44% |
| 每 chirp 的 RX | **4 个全齐**（RX0–3 各 1/4） | 4 个全齐 |
| chirp 索引 | **只出偶数**（18,20,…,62，32/64） | 0–63 全出 |
| 有效雷达帧率 | **7.6–7.7 帧/s** | 1.92 帧/s |
| 坏校验 | 1 / 2532 | 0 |

- 2532 个 72 B 帧 / 2.5 s，按 counter 回绕切帧：19 个完整帧 / 2.5 s = **7.6 帧/s**。
- 每帧 32 个 counter × 4 RX = 128 帧；counter 步进恒定 `0x20`，无整帧丢失。

### 9.4 判断修正

- §3「UART 1.5 Mbps 是硬约束」**在本配置下不成立**：130 ms 只要 70 kB/s，串口占用不到一半。
- `Chirp NOT complete[23]` 的直接原因是**每帧只出 32/64 个 chirp（偶数索引）**，
  不是数据没传完。缺的那一半在 chirp 时序/计数，不在 UART。
- 旧文按「32 bin / 4 RX / 34 kB 每帧」估出 130–260 kB/s，与实际（72 B 帧）差了 2–4 倍。

### 9.5 3 Mbps 尝试（已证伪，不要再试）

- 下发帧：`FD FC FB FA 08 00 12 00 08 00 C0 C6 2D 00 04 03 02 01`
  （`SetUartBaudrate` + u32 3000000，格式由 11/03 日志反解）
- 芯片回 `ACK status=0x0000`，命令被接受；
- 但 3 Mbps 下收 **0 字节**，Start 段无回包。两种切法都试过：
  重开串口、同句柄改 `baudrate`。
- 恢复 1500000 也无回包，靠重放 boot 序列（1.5 Mbps）才恢复出流。

结论：这块 DEV113P / 当前固件**不接受 3 Mbps 数据口**（或需要厂商工具的特殊流程）。
没有继续调的必要——就算切成功，带宽也不是当前瓶颈。

### 9.6 下一步（T2 决策要用的输入）

提帧率其实**已经达标**：7.6–7.7 Hz，是 1.92 Hz 的 4 倍，跳的腾空段可采 3 帧。
代价是每帧只有 32 chirp，多普勒分辨率减半。

1. ✅ **已实现**：`radar_protocol_dev113p` 支持动态 bin（72 B 帧）与 `stride` 映射；
   `radar_source` 用环境变量切换：
   `RADAR_2T4R_BINS=16 RADAR_2T4R_CHIRPS=32 RADAR_2T4R_STRIDE=2 RADAR_2T4R_FRAME_US=130440`。
   **真机复验 2026-11-05**：3.02 s 出 21 帧 = **6.95 Hz**，每帧 4 RX × 32 chirp × 16 bin，
   dropped 3 / gap_frames 1（首尾边界）。1T2R 路径不受影响（默认仍是 32 bin / 64 chirp）。
2. 待做：用 7 Hz 采一组跳蹲数据，验腾空帧数 ≥3；再决定「跳」走 2T4R 还是 1T2R。
3. **不要再用 ONELAB 的 `Chirp NOT complete` 判成败**：它对 2T4R 的 TDM chirp 计数口径不适用。
   判据改为「counter 回绕周期内的 32 chirp × 4 RX 是否填满」。
