# 贡献 2026-11-25：左右移机器学习真正接进产线，并给出「上线口径」实测

> 一句话：11-24 那份对比是**离线重放**（84% vs 67%）；今天把模型接进 `radar_actions.py`
> 当成一条新的判据 `crit='ml'`，**真跑产线代码**重测，得到 **70.5%（158/224）vs 规则 67.0%**，
> 延迟 1.30 s vs 1.68 s，误报 2.9/min vs 7.9/min。
> 全面占优，但优势不是「+17 个点」，而是「同准确率下误报少 63%、快 0.39 s」。

---

## 1. 为什么必须重测：离线口径把三件事放宽了

11-24 的对比脚本缓存 `px/py/energy/n` 序列后在整段数据上重放。它公平地比较了**分类器**，
但悄悄替实时链路做了三件它做不到的事：

| 实时链路的真实行为 | 离线重放的做法 | 后果 |
|---|---|---|
| 本次 push 的点数 < `min_pts` → **直接 early return，这一帧没有证据** | 拿上一帧的值 ffill，照样算一次证据 | 证据密度虚高 |
| 野值帧（`max_step` 剔除）同样 early return | 同上 | 同上 |
| `TARGET_LOST` → `_reset_track()`：lane 回 CENTER、确认/释放计数清零 | 完全不知道 | 事件数偏移 |

动作段内「本帧有检出」的比例实测只有 **51.7%**，所以第一条就把证据量砍掉近一半。
84% → 70.5% 的落差主要来自这里，不是模型变差了。

## 2. 新增/改动的代码

| 文件 | 作用 |
|---|---|
| `radar-pointcloud/lane_model.py` | 有效性闸门 + 12 维因果特征 + 纯 numpy 前向。**训练与实时共用同一份特征代码** |
| `radar-pointcloud/models/lane_mlp.json` | 导出权重、标准化参数、闸门参数、阈值（约 12 KB） |
| `radar-pointcloud/radar_actions.py` | 新增 `CRIT_ML='ml'`：`_mlbuf`（41 s 环形缓冲）、证据分支、`--crit ml --lane-model --ml-thr --ml-release` |
| `tools/train_lane_ml.py` | 训练 + 留一 + 四种口径（raw/skip/force/**rt=上线**）+ 等误报 + 导出 + 自检 |
| `tools/eval_lane_ml_runtime.py` | **上线口径评估**：真跑 `analyze_file`，同脚本内跑 `crit='ml'` 与 `crit='xbase'` 对比 |
| `tools/check_lane_feature_parity.py` | 实时 `build_feature_row` 与离线 `build_feature_matrix[-1]` 逐位比对（16/16，≤1.3e-13） |

「先判断信息是否有效」的实现就是闸门，只两项：

```
det32 >= 0.15   且   |ffill(px)| < 1.05
```

- `det32`：近 32 帧里「有检出」的比例。低于 0.15 = 这段基本没看到人，闭嘴。
- `|px| < 1.05`：满量程约 1.08，撞满 = 目标在视场边上（多半是那台静止的电脑）。
- 动作段通过率 **88.1%**、静止段拒收 **14.9%**（这是选这两项的依据）。

被砍掉的候选条件（都实测无效，别再捡回来）：

- `jit16 ≤ 0.05`（抖动）：动作段中位 0.0549 vs 静止段 0.0552，**完全重合**。
- `det8 ≥ 0.5`：动作段 p25 只有 0.12，等于把 81% 的动作帧挡掉。
- 「本帧必须有检出」：动作段 present 仅 51.7%，太苛刻。

## 3. 上线口径结果（`outputs/lane-eval/ml-runtime.json`）

16 个带真值录制、224 个动作段，两个判据走**完全相同的取数与打分路径**：

| 判据 | 命中 | 延迟中位 | 误报总数 | 误报/分钟 |
|---|---|---|---|---|
| **ML（闸门 + 神经网络，thr 0.60）** | **158/224 = 70.5%** | **1.295 s** | **143** | **2.9** |
| 规则 `xbase` | 150/224 = 67.0% | 1.684 s | 391 | 7.9 |

分组看：

| 分组 | ML | 规则 | 说明 |
|---|---|---|---|
| `lr3b/lr3c` | 87.5 / 93.8% | 87.5 / 93.8% | 打平——这两个文件正是规则门限被调过的地方 |
| `lr2-p1-*` / `lr2-jqz-*`（0.7–1.0 m） | 75–95% | 55–90% | ML 优势最大，`jqz-070` +35 点 |
| `once-*` | 70–80% | 50–70% | 低检出文件，ML 明显更稳 |
| `m2recap-*`（1.5–2.0 m） | 28.6% | 42.9 / 64.3% | **两者都塌**，几何问题，不是判据问题 |
| `seg-125/150`、`stride-150`、`ext-125` | 40–70% | 40–50% | 远站位，低检出 |

⇒ 结论：ML 的提升集中在 0.7–1.0 m 的低检出场景；1.25 m 以上换谁都不行。

阈值曲线（跟上表同口径，只换 thr）：

| thr | 命中 | 误报/分钟 |
|---|---|---|
| 0.40 | 77% | 8.8 |
| 0.50 | 75% | 5.8 |
| **0.60（默认）** | **70.5%** | **2.9** |
| 0.70 | 63% | 2.2 |

默认取 0.60：游戏里「莫名换道」比「慢半拍」更伤体验，而 0.60 已经用**规则一半的误报**
换到更高的准确率。要更灵敏用 `--ml-thr 0.50`。

## 4. 移植正确性：怎么证明「离线数字就是上线数字」

新增 `.deepworks/tmp/verify_ml_runtime.py`，分两层判定：

**第 1 层（模型移植）**——实时每帧的 `(ml_valid, p_left, p_right)` 与离线
`build_feature_matrix + LaneModel.proba` 逐帧比对：

- 16/16 文件通过，全局最大偏差 **5.0e-04**（正好是实时侧存 3 位小数的舍入量）；
- 闸门判定分歧 **0 帧**。

**第 2 层（状态机移植）**——把实时侧**自己产生的证据流**喂给离线 `emit_events_skip`：

- 13/16 文件事件逐条完全一致（同名、同刻）；
- 剩下 3 个文件各差 1 条，已定位为**记录精度**：离线只有 3 位小数，把 0.5996 舍成 0.600，
  恰好跨过 0.60。验证方式：实时阈值下调到 0.59，这 3 个文件立刻补齐
  （`lr3c` 37 → 39 条，补的正是 29.008 s 那条 LEFT）；调到 0.55 时 45 条。

### 顺手修掉的四个真实 bug

| bug | 现象 | 根因 |
|---|---|---|
| 双重标准化 | MLP 崩到 48% | `mlp_proba` 内部又标准化一次，调用处已经标准化过 |
| 无检出帧存 0.0 | 概率全偏（pL 0.325 vs 0.005） | 实时缓冲写 0.0、离线写 NaN，`log10(1e-6) = -6` 成野值。改 NaN 后逐帧差 **0.000** |
| 闸门广播错误 | `ValueError: (1,) vs (40,)` | px 序列 317 长、X 只有 1 行 → 改 `px_ff[-len(X):]` |
| `moved` 未初始化 | `UnboundLocalError` | ML 分支开头补 `moved = False` |

另外把离线 `emit_events_skip` 的语义改成与实时**逐条对齐**：

1. 无效帧要**清零**确认/释放计数（原来是「跳过」，等于偷偷放宽门限）；
2. 释放条件用 `max(p_left, p_right) <= 0.35`，不是 argmax 判 NONE；
3. 支持 `resets=` 传入 `TARGET_LOST` 时刻，复现 `_reset_track()`。

## 5. 怎么用

```powershell
# 真机跑 ML 判据（等价于把 crit 从 xbase 换成 ml）
python radar-pointcloud\radar_actions.py --port COM3 --crit ml
python radar-pointcloud\radar_actions.py --port COM3 --crit ml --ml-thr 0.50
python radar-pointcloud\radar_actions.py --port COM3 --crit xbase   # 1 秒切回规则

# 上线口径评估（约 8 分钟，跑 ML + 规则两路）
python tools\eval_lane_ml_runtime.py

# 重训（改了数据或特征之后）
python tools\train_lane_ml.py --top-k 1 --min-pts 1 --band 1.0,2.6 --epochs 500

# 特征一致性自检
python tools\check_lane_feature_parity.py
```

**注意 `--top-k 1` 必须配 `--min-pts 1`**，否则每帧裁成单点后失锁、检出率 0%。

## 6. 已知限制（写在结论旁边）

1. **离线 rt 口径与实时实测仍差约 8 点**（重训后离线 62%、实时 70.5%）。原因是离线没有
   建模 `TARGET_LOST` 复位（缓存里只存了 LANE 事件）。所以**以实时实测为准**，离线只用于选阈值。
2. **1.25 m 以上两者都塌**，当前几何只对 0.7–1.0 m 成立，跨站位需要重采。
3. **样本仍是 16 文件、最多 2 个受试者、单日采集**，泛化压力没真正验证过。
4. **单种子训练**，逐文件波动约 ±5 点。
5. **7.7 Hz 下限未触及**：1.30 s 延迟里大头是「0.8 s 滑窗 + 3 帧确认」，不是分类器。
6. **跳/蹲不在本次范围**：`models/jumpduck.json` 仍 `usable:false`（LOSO 58.8%，
   区间下界 42.2% < 随机），继续等 P0→T0→T1→T2 验证门。
