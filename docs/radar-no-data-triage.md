# 「已连接但没有数据」3 分钟排查

## 1. 先认清三个状态，别被绿灯骗

| 界面文字 | 判断依据 | 真实含义 |
|---|---|---|
| `已连接（单台）` | WebSocket 握手成功（`onopen`） | **只证明 8766 端口有服务在听**，不证明有人在推帧 |
| `⚠ 雷达未连接` | 从开始到现在**一帧都没收到**（`radarSeen`） | 数据流是空的 |
| `x = –` | 当前帧里没有可用的 `x` | 同上 |

> 两个同时出现 = 「端口通了，但一帧都没推」。
> 这是桥接器（bridge）最常见的一种故障，**跟游戏无关**。

## 2. 为什么一定是上游的问题，不是游戏

桥接器的发送循环是这样的（`tools/radar_bridge.py`）：

```python
if frame is not None:          # 一帧都还没解析出来 -> 什么都不发
    hub.broadcast(...)
```

- 上游**一帧都没来过** → 一个包都不推 → 页面「已连接 + 0 帧」；
- 只要来过 **1 帧** → 之后它会**无限重发最后一帧**（超过 `--stale` 秒会打警告）。
  这时游戏表现是**卡在某个 x 不动**，而不是「雷达未连接」。

所以看到「雷达未连接」，结论就只有一句：
**这次桥接器启动之后，上游从来没吐出过一帧。**

## 3. 60 秒定位

### 3.1 看桥接器那个黑窗口

| 窗口里最后一行 | 含义 | 处理 |
|---|---|---|
| 只有 `等待雷达的 UDP 0.0.0.0:8888 数据` | UDP 一个包都没进来 | 走 3.2 |
| 每 10 秒一行 `运行中：已推送 0 帧，在线客户端 1 个` | 同上，且页面确实连着 | 走 3.2 |
| `收到: {...}` 但紧跟 `解析失败` | 包进来了，`--parse` 选错 | 换 `json` / `kv` / `csv`，先加 `--print-sample` |
| 有 `已推送 N 帧`（N>0） | 上游是通的 | 问题在字段/量纲，去体检台 |
| 什么都没有（窗口空/报错退出） | 桥接器没起来 | 看报错，端口被占用就换 `--port 8767` |

### 3.2 上游 0 包，按这个顺序查

1. **端口对不对**：雷达实际发往哪个端口？`--udp-port` 必须一模一样，差一个数字就永远收不到。
2. **发到哪台机器**：雷达配置里填的目标 IP 是不是这台的局域网 IP？填成 `127.0.0.1` 时，雷达是别的设备就永远到不了。
3. **Windows 防火墙**：第一次运行 Python 会弹「允许访问」，点了取消就**永久静默丢包**。
   放行：`New-NetFirewallRule -DisplayName "radar-udp" -Direction Inbound -Protocol UDP -LocalPort 8888 -Action Allow`
4. **雷达只在有目标时发数据**：人离开板前、探测区外，很多毫米波雷达直接静默。站到 1.5 米正中再看。
5. **模式选错**：雷达是主动连过来的（TCP 客户端）就要用 `--from tcp-listen`，用 `--from udp` 会一直等。
6. **串口占用**：`--from serial` 时上位机软件没关，COM 口被独占，读不到任何字节。

### 3.3 「刚刚还可以，突然就不行」的两种典型

1. **之前是假活**：雷达早就停推了，桥接器一直在重发最后一帧撑着画面，重开桥接器后彻底归零。
   → 看桥接器窗口有没有 `上游已经 xx.xs 没有新数据了`。
2. **重开时参数没带全**：上次那个窗口是一直跑着的旧进程，新开的这条 `--from` / `--udp-port` 跟实际不一致。

## 4. 接进数据体检台（这是唯一能定量判死的地方）

```powershell
cd dual-radar-kit
python -m http.server 8000
```

浏览器打开 `http://localhost:8000/radar-diagnose.html`（**必须 http，https 会禁掉 `ws://`**）。

1. 左 / 右两个地址分别填 `ws://127.0.0.1:8766`、`ws://127.0.0.1:8767`（两台雷达各起一个桥接器，`--port` 不同）；
2. 点「连接」，状态会显示 **已连接 · 等待数据** —— 这句话不是成功，是提醒；
3. 看 **帧数**：
   - 一直是 0 → 上游没推，回第 3 节；
   - 有数字 → 看 Hz、间隔 p95、延迟 p50；
4. 填几何参数（站距、板高、俯仰、板间距、夹角、x 量纲），**必须实测**；
5. 「开始体检」→ 10 步，每步就位后点「记录这一次」→ 出 G0~G3 四道门 → 下载 JSON / 逐帧 CSV。

### 门槛（任一 FAIL 先修上游，别进游戏调阈值）

- G0 通路：≥20 Hz，间隔 p95/中位 ≤2.5，无 >500 ms 空洞，`ts` 100% 有效
- G1 坐标：静息 σ ≤0.18，右 > 左，40 cm 分离 ≥4σ，20/40/60 单调
- G2 时间：延迟 p95 ≤300 ms，两路到达差 p95 ≤120 ms
- G3 事件：静息跳/蹲帧占比 ≤6%，命中率 ≥80%，串扰 ≤10%

## 5. 双雷达别只连一台

向导里勾上 **「两台雷达：一台管左右，一台管上下」**，填两个地址。
只勾单台时：连左右那台 → 跳蹲永远没反应；连上下那台 → 换道永远没反应。
状态栏 `左右 已连接 · 上下 无数据` 才是完整信息，看到「无数据」就是那一路的上游断了。
