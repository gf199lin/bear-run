# 判定说明（工作 2）

## 一、两套实现

| 实现 | 文件 | 运行方式 | 用途 |
| --- | --- | --- | --- |
| 网页内 `JCDet` | `01-点云程序/radar-pointcloud.html` 第 1425~1576 行 | 浏览器打开点云页，点「校准」 | 正式链路用这份，事件经 `out` WebSocket 发给游戏侧 |
| Node 版 | `03-动作判定/radar-detect.js` | `node radar-detect.js --replay x.bin` 或 `--serial COM8` | 离线回放/批量验证，直接发 UDP 8888 |

两份算法同源，`JCDet` 特意不碰 DOM 与 Bus，就是为了网页与 Node 测试共用同一份代码（`test_jcdet.js` 直接调用）。

## 二、算法流程（JCDet v1）

1. **组帧**：收 ICL1240 的 64 chirp × 4 RX FFT1D 包，凑满 ≥230/256 格才算一帧（约 0.52 s/帧）。
2. **多普勒 DFT**：8 个虚拟通道（`parity*4+rx`），每通道沿同奇偶的 32 chirp 做 32 点 DFT，`bin0` = 零速。
3. **找人门**：静止的人没有多普勒，必须用 `bin0` 的能量剖面，在 0.70~1.58 m（`P_LO=4, P_HI=9`，0.176 m/门）里取峰值门。
4. **俯仰特征**：同一门内，取最强多普勒 bin 的相位，`el = [φ5−φ2, φ2−φ3]`（垂直天线对的相位差）。
5. **校准**：收 6 帧（≈3.1 s）；**只用「安静帧」**（活跃度 `act < 0.35`）算基线，避免挥手/走动把基准带偏
   （踩过的坑：挥手时人门会锁到 1.4 m，而静站是 0.9 m）。最多等 40 帧，超时取最安静的 6 帧。
6. **判定**（`dev = el − elBase`，只看 `dev[1]`）：

| 条件 | 结论 |
| --- | --- |
| `|dev| ≥ 18°`（单帧）且次帧回落 | 跳 `jump` |
| 连续 2 帧 `|dev| ≥ 12°` | 蹲 `crouch_start` |
| 蹲中 `|dev| < 7°` | 起身 `crouch_end` |
| 单帧 `≥12°` 但没到 18° | 丢弃（普通晃动） |

7. **基线慢漂**：非事件帧且 `|dev|<7°` 时 `elBase += 0.03*dev`（≈17 s 时间常数），抵抗站位微移。
8. **玩家离开**：`bin0` 能量连续 4 帧低于基准的 35% → 自动重新校准。

**为什么用「持续时长」判跳蹲而不是符号**：板子倾斜、安装高度都会把 `dev` 的正负翻过来，时长不会，所以免标定方向。

## 三、阈值表

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `GATE_M` | 0.176 m | 距离门宽度（ICL1240） |
| `P_LO / P_HI` | 4 / 9 | 人门搜索范围 0.70~1.58 m |
| `TH_ON` | 12° | 事件起始阈值 |
| `TH_OFF` | 7° | 事件结束（回落）阈值 |
| `TH_SPIKE` | 18° | 判「跳」的单帧尖峰阈值 |
| `CALIB_N` | 6 帧（≈3.1 s） | 校准所需安静帧数 |
| `QUIET_R` | 0.35 | 安静帧门限（多普勒活跃度占比） |
| `LOST_N / LOST_R` | 4 帧 / 35% | 判玩家离开 |

## 四、离线验证

- `extract_jc.js`：从点云页导出的事件流中抽出判据输入，转成可回放格式。
- `test_jcdet.js`：把 `JCDet` 这段代码原样取出来，喂真实 `.bin` 回放，逐帧打印 `dev0/dev1` 与判定结果。
- `analyze_v2.js`：按剧本（挥手→静站→10 跳→10 蹲→负样本→连招）分段统计，输出三类特征的判别力与逐次一致性。
- `diag_jc*.js`：卡在「误报」时定位到底是相位、增益还是距离门的问题。

**结论（如实写）**：v1 在旧板数据上 `dev[1]` 接近白噪声，离线误报率 85%~91%，判据不可用；
因此代码里 `observeOnly` 默认开，跳蹲事件不发进游戏。等新板干净数据采到后按 `analyze_v2.js` 的
「活动量包络 + 多普勒展布 + 落地冲击」三特征重定 v2 阈值再放开。
