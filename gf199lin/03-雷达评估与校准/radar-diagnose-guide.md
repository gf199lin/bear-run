# 双雷达联调：连接成功之后要做什么

> 适用版本：`radar-runner` 双雷达（`RADAR.dual = true`，左右一路 + 上下一路）
> 新增工具：`radar-runner/radar-diagnose.html`（雷达数据体检台）
> 写给：游戏组（C/D）+ 数据组（A/B）+ 现场同学

---

## 0. 一句话

**连接成功只是第 0 关。** 真正决定能不能玩的是四道数据门：**通路 → 坐标 → 时间 → 事件**。
任何一道不过，游戏侧改判定阈值都救不回来——上一批数据已经证明了这一点（跳/蹲判据 FPR 89%，左右方向准确率 53.3%）。

所以你们现在最该做的不是"再调调游戏"，而是**把"不准"变成一张能落到具体责任方的数字表**。

---

## 1. 先分工，别互相等

| 角色 | 负责 | 具体交付 |
|---|---|---|
| **数据组（A/B）** | 雷达侧：帧率、字段、量纲、几何、时钟、判据 | 每帧一个 JSON、≥20 Hz、物理量单位、`geometry.txt` 无 `not-measured` |
| **游戏组（C/D）** | 判定侧：体检台、校准、回放、降级、HUD 提示 | 一份体检报告结论 + 一个"不过门就不进游戏"的开关 |
| **现场** | 动作脚本、站位、真值 | 按第 6 节做动作；标尺/地贴；手机录像做对时 |

**边界要提前说清：**
- 雷达采样率、坐标系、跳/蹲判据，**游戏侧无法补偿**（漏采的动作不会因为阈值变低而回来）。
- 游戏侧能做的只有三件事：**现场学零点/极性、按噪声自动收紧或停用动作、不可用时干净退回键盘**。

---

## 2. 两路都连上后，30 分钟内做完这 5 件事

### ① 两路各跑一次链路检查（数据组，2 分钟）

在雷达那台机器上，对两个地址各跑一次：

```bash
python tools\check_radar.py ws://127.0.0.1:8766
python tools\check_radar.py ws://127.0.0.1:8767
```

看它报的 ①TCP / ②握手 / ③帧 / ④字段 / ⑤数据质量，哪层 `[FAIL]` 就先修哪层。
**先别进游戏**——链路层没通，游戏里的现象没有诊断价值。

### ② 填现场几何（现场，3 分钟）

必须实测、写实数，禁止"大概"：

| 项 | 怎么测 | 为什么必须 |
|---|---|---|
| 站距（人到板） | 卷尺 | 决定 x 的比例尺 |
| 板高 | 卷尺到板中心 | 决定上下维是否看得到 |
| 俯仰角 | 手机水平仪 | 历史上板没瞄准人 = 左右直接不可分 |
| 两板间距 / 夹角 | 卷尺 + 量角 | 两块板覆盖区是否重叠到同一个人 |
| x 量纲 | 问数据组 | 归一化 / 米 / 像素，决定阈值能不能直接用 |

### ③ 跑一次标准体检（现场 + 游戏组，2.5 分钟）

打开 `radar-runner/radar-diagnose.html`：

1. 填两路 ws 地址 → 分别点「连接」；
2. 填第 ② 步的几何信息；
3. 点「开始体检」，按屏幕提示做 10 步（静息 → 左 20/40/60cm → 右 20/40/60cm → 跳 ×5 → 蹲 ×5 → 再静息）；
4. 每步**先就位，再点「记录这一次」**；单步没做完不要点「跳过」；
5. 结束后看第 ⑤ 节结论。

### ④ 导出并回传（游戏组，1 分钟）

报告页三个按钮：

- **下载 JSON 报告** —— 指标 + 判定 + 几何，给游戏组存档；
- **下载逐帧 CSV** —— 原始帧，给数据组离线复算；
- **复制文字摘要** —— 直接贴群里。

> 体检台只读：不写校准存档、不改游戏配置。导出文件在浏览器下载目录。

### ⑤ 当场对结论（双方，5 分钟）

按第 3 节的四道门逐条过。**任何一条 FAIL，先修上游，不要进游戏调阈值。**

## 3. 四道门（验收口径）

体检台用的就是这套阈值，和游戏内校准探针同口径。

### G0 通路门（不过就别谈准不准）

| 指标 | 通过 | 警告 | 不合格 | 谁修 |
|---|---|---|---|---|
| 每路帧率 | ≥ 20 Hz | 10–20 Hz | < 10 Hz | 数据组 |
| 间隔稳定性 p95/中位 | ≤ 2.5 | ≤ 4 | > 4 | 数据组 |
| > 500 ms 空洞 | 0 次 | — | ≥ 1 次 | 数据组 |
| `ts` 有效率（毫秒时间戳） | 100% | — | 缺失 | 数据组 |

**为什么卡 20 Hz**：跳的腾空约 0.5 s。1.92 Hz 只能采到 1~2 帧，动作在数据里根本不存在；7.72 Hz 也已经让手感明显发钝。

### G1 坐标门（"不准"最主要出在这里）

| 指标 | 通过 | 不合格 | 谁修 |
|---|---|---|---|
| 静息 x 标准差（归一化） | ≤ 0.18 | > 0.29 | 数据组 |
| 左右方向 | 右 > 左 | 右 ≤ 左 | 数据组（先排极性，再排几何） |
| 40 cm 档左右分离度 | ≥ 4σ | < 2σ | 数据组 |
| 20/40/60 cm 单调性 | 全部递增 | 有回落 | 数据组 |
| 线性度 CV（\|Δ\|/cm） | ≤ 0.30 | > 0.51 | 数据组 |
| x 贴边饱和比例 | ≤ 5% | > 15% | 数据组 |
| 回到基线 | ≤ 2σ | > 3.6σ | 数据组 |

- **方向反了**先让桥接器加 `--invert-x`，一次就能排掉；
- 加了还反，或者左右都往同一边走 → **不是符号问题，是没采到方向信息**（上一批 `lr-move` 就是这样：RIGHT 去基线后仍是负位移 0.07~0.16 m）；
- 20 cm 有反应、60 cm 不再变大 → 饱和或出视场，先查板有没有瞄准人。

### G2 时间门（双雷达新增，最容易漏）

| 指标 | 通过 | 不合格 | 谁修 |
|---|---|---|---|
| 单路端到端延迟 p95 | ≤ 300 ms | > 600 ms | 数据组 |
| 两路到达时间差 p95 | ≤ 120 ms | > 200 ms | 游戏组 / 数据组 |
| 两路采集时刻偏斜 | 同源时钟下 ≤ 50 ms | 时钟不同源 | 数据组 |

> 延迟要用**采集时刻**的 `ts`，不是发送时刻。跨机器时两边必须 NTP 对时，否则这个数没有意义。
> 两路帧率差太大（比如 30 Hz + 8 Hz），到达差必然超 120 ms——这不是"时钟问题"，是慢的那路在拖后腿。

### G3 事件门（决定角色会不会自己乱动）

| 指标 | 通过 | 不合格 | 谁修 |
|---|---|---|---|
| 静息时 jump/crouch 帧占比 | ≤ 6% | > 15% | 数据组 |
| 静息误报事件数（约 18 s） | ≤ 2 | ≥ 3 | 数据组 |
| 跳 / 蹲命中率（各 5 次） | ≥ 80% | < 60% | 数据组 |
| 非对应动作段误报（串扰） | ≤ 10% | > 10% | 数据组 |

> 静息误报高时，游戏会在校准第 1~3 步自动判 `noisy`，**停用跳/蹲并退回键盘**。
> 这是有意降级，不是 bug。要恢复只能修上游判据。

## 4. "数据不准"的九种表现 → 先查什么

| 现场看到的现象 | 最可能的根因 | 用体检台怎么确认 | 谁修 |
|---|---|---|---|
| 人左右走，x 几乎不动 | 探测区没人 / x 写成常量 / 出视场 | 曲线贴水平线；单调性 NA | 数据组 |
| x 动，但左右反 | 极性装反 | 方向门 FAIL，但分离度正常 | 数据组（`--invert-x`） |
| 左右都往同一边 | 没有方向信息（只测径向） | 方向 FAIL + 分离度 ≈0 | 数据组（要角度维/双 Rx 相位差） |
| 站着不动 x 一直抖 | 上游噪声 / 多人 / 多径 | 静息 σ > 0.18 | 数据组 |
| 20 cm 有、60 cm 没 | 饱和或出视场 | 单调性回落 + 饱和比例高 | 数据组（调安装角度/量程） |
| 动作慢半拍、画面滞后 | 帧率低 / 滤波过度 / 时钟不同步 | 帧率 < 20 Hz、延迟 p95 > 300 ms | 数据组 |
| 没跳却自己跳 | 上游判据零判别力 | 静息误报 > 6% | 数据组（重做判据） |
| 真跳不触发 | 漏检 / 帧率太低采不到 | 命中率 < 60% | 数据组 |
| 边跳边换道就错位 | 两路不同步 | 两路到达差 p95 > 120 ms | 游戏组（按 ts 对齐或合桥） |

**优先级**：先修帧率（最便宜、收益最大）→ 再修安装几何/瞄准 → 最后才谈判据。
帧率 1.92 Hz 时，后面所有统计都不可信。

## 5. 双雷达专属的 7 个坑

1. **两路的零点和极性各自独立。**
   游戏里的校准（`x₀`、`sign`）只作用在左右那台；上下那台只提供 `jump/crouch/height`。
   不要让数据组"把两台调成一样的零点"，没意义。

2. **两路时钟不同源。**
   两台雷达各打各的 `ts`，游戏合并帧时用的是**到达时间**（`Date.now()`，见 `js/InputSource.js` 的 `_rebuildMerged`）。
   帧率低或网络抖动时，x 和 jump 会错位。**最省事的修法：让数据组把两路合到一个桥接器，输出单路合并帧。**

3. **两路覆盖区必须重叠到同一个人。**
   左右板看横向、上下板看纵向，但人只有一个。两板夹角太大 = 一个人不可能同时处在两个视场里。

4. **上下那路的 `x` 会被清零。**
   `pickRoleFrame()` 在进解码器前就把不该它管的维度清零了（左右路的 `jump/crouch/height` 归 0，上下路的 `x` 归 0）。
   所以上下雷达给不给 `x` 都无所谓，**但别指望用它来救左右**。

5. **一路掉线时会"旧值续命"。**
   当前合并帧直接取两路的 `lastRaw`，一路断了以后它的最后一个值仍在参与合并，直到 500 ms 超时判定断开。
   如果现场出现"跳完一直保持跳"，先看是不是上下路断了。这条已列入游戏侧待办（见第 10 节）。

6. **整体帧率取两路的较小值。**
   `DualRadarInputSource.update()` 里 `frameRate = min(lr, ud)`。所以**慢的那一路决定体感**，
   优化只快一路没有意义。

7. **两台会互相干扰，但先分清是"数据串台"还是"射频互扰"。**
   前者是地址/端口/桥接器配错，后者是天线收到了对方的 chirp。两者的现象很像，处理方式完全不同。详见 5.1。

### 5.1 射频互扰：怎么判断、怎么解

**先分清两种"干扰"：**

| 类型 | 典型表现 | 怎么区分 |
|---|---|---|
| 数据串台（软件） | 两路数值几乎一样；挡 A 时 B 也跟着变 | 手挡测试；检查两路是不是不同端口、不同桥接器 |
| 射频互扰（硬件） | 单开正常，双开噪声抬升、出现假目标、帧率下降 | 单台 / 双台 两段静息对比（体检台 ③·5） |

**机理**：FMCW 雷达 A 发射的 chirp 会被 B 的天线收到。两台的起始频率、斜率、周期不完全一致时，
A 的信号在 B 混频后变成一个拍频，落在 B 的距离谱上——表现为一根假距离条，或整体被抬高的噪声底。
两台正对且距离近时，直达波还会让前端 AGC 饱和，真实目标反而被压掉。

**会不会干扰，取决于 4 件事：**

1. **频段**：24GHz ISM 只有 250MHz，同型号默认配置基本必然同频，互扰概率最高；
   60GHz 波束窄、大气衰减大，概率低很多；UWB 靠信道/PRF 区分，同信道才会互相压制。
2. **朝向与间距**：正对且 <1m 最糟；背对/侧对、间距 >1.5m 明显好转。
3. **配置是否可改**：能改起始频率/带宽/chirp 的可以做频分；消费级 1T2R 模块通常不开放这些参数。
4. **距离门**：只看到 2~3m 时，远端的对方会落在门外，等于天然屏蔽。

**处理顺序（成本从低到高，前两步通常就够了）：**

1. **空分 + 转向**（免费，最有效）：两板不要正对；间距 ≥1~1.5m；让波束只在玩家身上交叠。
2. **遮挡**：两板之间加金属隔板或吸波材料，阻断直达波。隔板必须放在视场外，否则多径会更糟。
3. **距离门 / 功率**：最大距离压到 2.5~3m；模块支持的话把发射功率降一档。
4. **频分**：改起始频率/带宽，让两台工作频段不相交。24GHz 总共只有 250MHz，
   各分 100~120MHz 已是极限，代价是距离分辨率下降。
5. **时分 / 同步**：主机模式或外部触发交替发射，需要 GPIO/同步线，消费级模块基本没有。
6. **极化**：一横一竖正交，理论 10~20dB，但会改变覆盖方向图，必须实测。
7. **处理层兜底**：各自距离门 + 角度门、单帧跳变剔除、串扰帧标记。只能减轻，不能消除。

**10 分钟自测（体检台 ③·5 已内置）：**

1. 只连左右雷达（上下雷达断电或断开 ws），站定，点「采单台 20 秒」；
2. 连上上下雷达，保持同一站位，点「采双台 20 秒」；
3. 看自动对比：**σ 比值 ≥1.5、跳变 +3 次以上、或帧率 <75%** → 判互扰；
4. 拉开间距或换朝向后重测，看比值是否下降。

**先做手挡测试**：用铝箔/吸波棉只挡 A 的天线面，看 B 的 x 是否变化。
变了说明是数据串台或强耦合，不是"雷达算法不准"。

**你们这种布局的建议：**

- 左右板放正前方略低（看横向），上下板放侧上方约 45°（看纵向），**不要并排同向**；
- 两板间距 ≥1m，中间加隔板；
- 若只能同向：上下板距离门 0.5~2.5m，左右板 0.5~3.5m，并上下错开 ≥30cm；
- 先确认两路是两个独立 ws（不同端口/不同桥接器），别把"串台"当"干扰"。

## 6. 现场动作脚本（照这个念）

体检台的 10 步就是标准脚本，这里给出对应的物理动作，方便现场同学执行：

| 步 | 动作 | 次数 | 要点 |
|---|---|---|---|
| 1 | 站中间不动 | 10 s | 双手自然下垂，别说话别晃 |
| 2 | 向左 20 cm | 3 | 走一小步，站定 1.6 s |
| 3 | 向左 40 cm | 3 | 比上一步再远一点 |
| 4 | 向左 60 cm | 3 | 接近视场边缘；若 x 不再增大就是饱和 |
| 5 | 向右 20 cm | 3 | 对称做 |
| 6 | 向右 40 cm | 3 | 对称做 |
| 7 | 向右 60 cm | 3 | 右侧历史上最容易出视场 |
| 8 | 原地起跳 | 5 | 正常起跳，别助跑；落地站稳再点 |
| 9 | 原地下蹲 | 5 | 正常下蹲 |
| 10 | 回原位站定 | 8 s | 看 x 能不能回到基线 |

**必须做到的 4 件事：**

1. 地面贴刻度（0 / ±20 / ±40 / ±60 cm），不要靠目测；
2. 每个动作之间回中间，间隔 2~3 s；
3. 全程手机录像，画面里带一个可见的时间码（用于事后对时）；
4. 探测区里只站一个人，旁边的人退到视场外。

## 7. 下一批数据采集的硬要求（给数据组）

按优先级，前三条不做，后面的统计都没意义：

1. **帧率 ≥ 20 Hz，`dropped` < 1%**（当前处理链 4:1 降采样是瓶颈，硬件 30.9 Hz 本身达标）；
2. **动作交错随机化**：不要 LEFT×7 → RIGHT×7 分块连做。随机顺序 + 随机间隔，把种子和实际顺序写进 labels；
3. **每个动作 ≥ 30 次，分小/中/大三档幅度**，并记录真实横向位移 `dx_m`（cm 级）；
4. `geometry.txt` 禁止 `not-measured`：板高、俯仰、站距、朝向、两板相对位置；
5. 开头/结尾各 60 s 静息，中间插 2 段 30 s 空白（用于估漂移）；
6. 单人 ≥ 2 次 session、总共 ≥ 5 人；
7. 交付**逐帧特征 JSONL**（`frame/t/e_total/peak_range_m/v_lat/n_pts/occ`），不要只给结果表。

## 8. 通过标准（可以直接拿去验收）

| 项目 | 门槛 |
|---|---|
| 每路帧率 | ≥ 20 Hz，`dropped` < 1% |
| 左右方向 | 40 cm 档分离 ≥ 4σ，方向正确，20/40/60 单调 |
| 左右线性度 | CV ≤ 0.30 |
| 静息噪声 | σ ≤ 0.18（归一化） |
| 静息误报 | 帧占比 ≤ 6%，事件 ≤ 2 / 18 s |
| 跳 / 蹲命中 | ≥ 80%，串扰 ≤ 10% |
| 延迟 | p95 ≤ 300 ms |
| 双路同步 | 到达差 p95 ≤ 120 ms |

**这 8 条全过，游戏侧才认为"雷达可用"；否则按第 4 节定位，不进入玩法排期。**

## 10. 游戏侧待办（连接成功后我们这边要做的事）

按优先级：

1. **把体检台作为现场第一入口**（已完成：`radar-diagnose.html`）。
   以后每次换场地/换人/挪板，先跑 2.5 分钟，再进游戏。
2. **双路时序对齐**（待做，G2 不过时再做）：
   现在是按到达时间合并（`_rebuildMerged` 用 `Date.now()`，直接取 `lastRaw`）。
   若两路延迟差 > 120 ms，应改成按各自 `ts` 做最近邻配对，并给合并帧标注实际配对误差。
3. **旧值续命**（待做）：
   一路超过 `staleMs` 没新帧时，合并帧不应继续使用它的 `lastRaw`；
   应把该维度置为"无数据"（x 用 `NaN`，jump/crouch 归 0），避免"跳完一直跳"。
4. **不过门就不进游戏**：
   校准探针已经会在静息误报超限时停用跳/蹲；建议在联调台/菜单再加一句显式提示
   （"体检未通过：本局建议键盘"），避免现场硬上。
5. **准备降级 demo**：
   键盘 + 相机两条路都保留。雷达不过门时，演示直接切键盘，不要在台上现调。
