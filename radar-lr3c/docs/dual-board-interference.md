# 双板共存：1T2R（左右）+ 2T4R（跳蹲）会不会互相干扰

> 状态：**分析 + 待实测**。本文的数字里，射频参数来自 `docs/radar-uplink-dev113p-2t4r.md` L200-210 与协议实测；
> 干扰强度是**雷达方程估算**，不是实测值。**没有任何一次"两板同时工作"的录制**（全仓库只有单板文件）。

---

## 0. 先说结论

| 问题 | 结论 |
|---|---|
| 会有射频干扰吗 | **会。** 两板频段重叠，且 1T2R 的整个带宽落在 2T4R 的扫频范围内 |
| 干扰是什么形态 | **抬高噪声底**（不是单个假目标）——因为两板 chirp 斜率不同（1.04 vs ≈5 MHz/µs） |
| 串口会冲突吗 | **不会。** 1T2R 是 CP210x/COM3/921600，2T4R 是 FTDI/COM4/1500000，芯片和端口都不同 |
| 软件能同时跑吗 | **能**，但当前是单板架构，要起**两个 `server.py` 实例 + 两个 `--http-port`**，前端要消费两路 |
| 2T4R 能辅助左右判断吗 | **不建议。** 它只有 **1.92 Hz**，比 1T2R 慢 4 倍，做左右会直接拖垮延迟 |

**一句话**：能一起用，但**必须做物理隔离并实测**；而且 2T4R 只该干"跳/蹲"这一件事。

## 1. 两块板的射频参数（都是 24 GHz 频段，但配置差很多）

| | 1T2R（DEV202H / ICL1122） | 2T4R（DEV113P） |
|---|---|---|
| 中心频率 | **24.125 GHz** | **24.5005 GHz** |
| 带宽 B | **220 MHz** | **999 MHz** |
| 占用频段 | 24.015 ~ 24.235 GHz | **24.001 ~ 25.000 GHz** |
| 波长 λ | 12.43 mm | 12.24 mm |
| 距离门距 | 0.6813 m | 0.15 m |
| 帧周期 | **0.1295 s（7.7 Hz）** | **0.5208 s（1.92 Hz）** |
| 水平阵元间距 | 6.250 mm | 5.900 mm |
| 串口 | COM3 / CP210x / 921600 | COM4 / FTDI / 1500000 |

**关键一行**：1T2R 的 **24.015~24.235 GHz 完整落在** 2T4R 的 24.001~25.000 GHz 之内。
⇒ 两板不可能靠"频率错开"共存，**硬件层面无法规避**。

## 2. 干扰形态：为什么是"抬高噪底"而不是"假目标"

FMCW 雷达之间干扰的产物是**拍频**：

```
f_beat = |f_A(t) − f_B(t)|
```

- **如果两板斜率相同**：拍频近似恒定 → 落在**某一个距离门** → 表现为一个假目标（好处理）。
- **如果两板斜率不同**：拍频随时间扫过一段范围 → 散布到**多个距离门** → 表现为**噪声底整体抬高**（难处理）。

实测参数：

| | 1T2R | 2T4R |
|---|---|---|
| 带宽 / 扫频时间 | 220 MHz / 212 µs | 999 MHz / 未测 |
| 斜率（估） | ≈ **1.04 MHz/µs** | ≈ **5 MHz/µs**（若扫频时间同量级） |

⇒ **斜率差约 5 倍 ⇒ 属于"抬高噪底"这一类，最坏的那一类。**

**不对称性（对我们有利的一点）**：

- **2T4R → 1T2R**：2T4R 扫 1 GHz，扫过 1T2R 的 220 MHz 时都会产生干扰 ⇒ **污染 1T2R 的全部距离门**。
- **1T2R → 2T4R**：1T2R 只占 220 MHz，只影响 2T4R 扫频的 **约 22%** ⇒ **只污染 2T4R 的一部分距离门**。

而 2T4R 只用来测"人在 1 m 附近"的俯仰角，**距离门是已知且窄的**，
所以"1T2R 干扰 2T4R"这一半相对可控；**"2T4R 干扰 1T2R"才是主要风险**。

## 3. 干扰强度估算（雷达方程，非实测）

自由空间直接耦合：

```
P_干扰 / P_发射 = (λ / 4πd)²          → 20log10(λ/4πd)
```

目标回波（人，RCS ≈ 0.5 m²，距离 1 m）：

```
P_目标 / P_发射 = G²λ²σ / ((4π)³R⁴)
```

取 G = 5 dBi/天线（保守），λ = 12.4 mm：

| 两板间距 d | 直接耦合 | 相对目标回波 |
|---|---|---|
| 0.20 m | −46.1 dB | **强 18 dB** |
| 0.30 m | −49.6 dB | 强 14.5 dB |
| 0.50 m | −54.1 dB | 强 10 dB |
| 1.00 m | −60.1 dB | 强 4 dB |

⇒ **两板靠近且主瓣相对时，干扰比人体回波强 10~18 dB。**
但天线有方向性：若两板**背对背**，主瓣互不照射，隔离度可再加 20~30 dB，
此时干扰会落到目标回波之下。

**这与 `#51` 的实测是一致的**：单板时噪声底约 `1.15e4`（左）/ `9716`（中）/ `1.18e4`（右），
两板互扰会把这个数字整体推高。**验证方法就是对比"单开 vs 双开"的噪声底。**

## 4. 串口与软件层：不冲突，但要改架构

### 4.1 串口层：干净

| | 芯片 | 端口 | 波特率 |
|---|---|---|---|
| 1T2R | CP210x | COM3 | 921600 |
| 2T4R | FTDI | COM4 | 1500000 |

不同芯片、不同 COM、不同速率 ⇒ **物理上互不干扰**。
（注意 `AGENTS.md` 记的"CP210x 驱动"只针对 1T2R；2T4R 走 FTDI，驱动另装。）

### 4.2 软件层：当前是单板设计，要动

`server.py` 已经是参数化的：

```
--port       串口（auto / COM3 / COM4）
--board      auto / 1t2r / 2t4r
--http-port  默认 8099
```

所以两板共存的最小改造是**起两个实例**：

```powershell
# 1T2R：左右主链路
python radar-pointcloud\server.py --port COM3 --board 1t2r --http-port 8099

# 2T4R：跳/蹲
python radar-pointcloud\server.py --port COM4 --board 2t4r --http-port 8100
```

**但下面这三件事必须一起解决，否则跑了也没用**：

| 问题 | 说明 |
|---|---|
| **前端只认一个源** | `radar-runner/js/InputSource.js` 消费单个 ws/SSE，要改成双源并合并 |
| **事件语义冲突** | 两个实例都会输出 `LANE_*`/`JUMP`/`DUCK`。必须约定：**8099 只取 LANE，8100 只取 JUMP/DUCK**，否则互相打架 |
| **时间戳对齐** | 两板独立晶振、帧周期 129.5 vs 520.8 ms，2T4R 一帧跨 4 个 1T2R 帧。融合时要按**到达时间**对齐，不能按帧号 |

> 另注：`capture-checklist.md` §0.6 提到"跑采集前要先停 8099 服务（它独占 COM4）"——
> 那是采集脚本与 server 争**同一个**串口的情形，不是双板互斥。只要各自指向不同 COM 即可。

## 5. 2T4R 到底该不该"辅助左右"——参数上就不该

用户设想的三种角色，逐条对一下：

| 角色 | 2T4R 能不能胜任 | 依据 |
|---|---|---|
| 测跳/蹲 | ✅ **能** | 俯仰角通道可用（`VertAngleInfo = 5.900,1.000,0,2;5,2,3`），动作慢，1.92 Hz 够 |
| 辅助左右判断 | ❌ **不该** | **1.92 Hz**：一次左右移动约 0.6~1.0 s，只剩 1~2 帧；而 1T2R 有 5~8 帧。加进来只会**拖慢**而不是帮忙 |
| 提高左右精度 | ❌ **不明显** | 左右靠的是**方位角**，两板水平阵元间距 6.25 vs 5.90 mm，差别很小；2T4R 的优势在**俯仰**，不在水平 |

**建议**：**左右只由 1T2R 做，2T4R 只做跳/蹲。** 让 2T4R 参与左右，收益为负。

> 顺带一个与 `AGENTS.md` 硬约束 5 相关的事实：2T4R 的俯仰通道组合存在，
> 但**虚拟通道索引到物理天线高度的映射仍未确定**（`radar-uplink-dev113p-2t4r.md` L106-108），
> 所以"能测高度"还不是已证结论，只是"有通道"。

## 6. 验证方案（设备可用后，约 30 分钟）

**唯一需要回答的问题：双开时 1T2R 的噪声底抬高多少？**

```
A 段：只开 1T2R，空场静置 60 s       → 记 j0..j7 噪底
B 段：只开 2T4R，空场静置 60 s       → 记噪底
C 段：两板同时开，空场静置 60 s     → 记 1T2R 噪底
D 段：两板同时开 + 人在 1 m 做左右   → 看 LANE 命中率是否掉
```

判据（提案，待小组确认）：

| 指标 | 可接受 | 需处理 |
|---|---|---|
| **C 段 1T2R 噪底抬升** | **< 3 dB** | ≥ 3 dB 就要加隔离 |
| D 段左右命中率相对 A 段下降 | < 10 个百分点 | ≥ 10 就要重排安装 |

**安装建议（按性价比）**：

1. **背对背 + 拉开 ≥ 0.5 m**（利用天线方向性，最先做，成本零）
2. 两板之间加**吸波材料**（金属板反射会二次耦合）
3. 让 2T4R 的天线法线**避开** 1T2R 的主瓣方向
4. **不要**指望改频率——硬件固定，改不了

## 8. 2026-10-29 实测：双板同插时的端口身份与 2T4R 静默

两块板同时插在同一台电脑上，用 `.deepworks/tmp/identify_dual.py`（只读探针）
做三重交叉识别：USB VID:PID、`radar_source.probe_board()` 硬件指纹、实测字节流。

| 端口 | USB-UART | VID:PID | probe_board | 实测字节流 | 判定 |
|---|---|---|---|---|---|
| COM3 | CP2102 | `10c4:ea60` | `1t2r` | 38.2 KB/s，连续 6 s 稳定 | **1T2R 确认** |
| COM4 | FT232 | `0403:6001` | `2t4r` | **0 B / 6 s** | 硬件在线，**板子未出数** |

### 8.1 一个口径更正：1T2R 当前走「裸帧模式」

实测 1T2R 是 **38.2 KB/s**，不是 §1 表里按 52 B/包推算的 50.3 KB/s；
且 `ICLH` 魔数命中 **0** 次。这与 `radar_source.py` L147 的
`NAKED_1T2R_PKT = 40`（裸帧 40 B/包）一致：991 × 40 ≈ 39.6 KB/s。

**结论**：38 KB/s 是 1T2R 裸帧模式的正常值，不是链路故障。
`docs/radar-uplink-dev113p-2t4r.md` 里「52 B/包」对应的是 ICLH 包裹模式，两者要分开看。

### 8.2 2T4R 静默的排查边界

`.deepworks/tmp/diag_com4_silent.py` 做了软件侧穷举，全部 **0 字节**：

- 波特率：1500000 / 921600 / 460800 / 230400 / 115200 / 2000000 / 3000000
- DTR/RTS：`True/True`、`True/False`、`False/True`、`False/False`

**关键判据**：若只是波特率不匹配，会读到**乱码字节（非零）**；
读到**严格 0 字节**说明板子在物理层没有发送。⇒ 软件侧已排除，
问题在供电、线序（FTDI RX ↔ 板 TX）或固件状态。

拔插 USB 后仍为 0 字节 ⇒ 不是「临时停在命令模式」。

### 8.3 一个可以立刻用上的推论

若 2T4R 只是「通电但串口不出数」，它是否仍在发射射频是**未知**。
这一点不必靠猜 —— **把 1T2R 当探测器**：对比「2T4R 断电」与「2T4R 通电」两段
1T2R 的噪底，若后者明显抬高，就说明 2T4R 即使不出数也在发射。
该对比**不依赖 2T4R 的串口是否能出数**。

### 8.4 证据等级

| 结论 | 等级 |
|---|---|
| COM3=1T2R / COM4=2T4R（三重交叉一致） | **[已执行·可复现]** |
| 1T2R 裸帧模式 38 KB/s 为正常值 | **[已执行·可复现]** |
| 2T4R 软件侧全组合 0 字节 | **[已执行·可复现]** |
| 2T4R 通电时是否仍在发射 | **[未验证]** |
| 双开噪底抬升量 | **[仍未测]**（2T4R 不出数，A/B/C 无法成立） |

## 9. 2026-10-29 复核：对换接口后重测

用户交换两个雷达的接口后，用 `.deepworks/tmp/swap_check.py` 重测
（每口在 921600 / 1500000 下各读 2.5 s）。

| 端口 | 芯片 | @921600 | @1500000 | 数据判定 |
|---|---|---|---|---|
| COM3 | CP2102 `10c4:ea60` | 37.6 KB/s，`55AA`×2406，间距 **40 B** | 乱码（`55AA`×0） | **1T2R** |
| COM4 | FT232 `0403:6001` | **0 B** | **0 B** | 无数据 |

### 9.1 关键结论：对换没有改变芯片↔板子的对应关系

CP2102 背后仍是 1T2R、FT232 背后仍是 2T4R。
唯一变化是 CP2102 的 USB 位置由 `Port_#0004` 变为 `Port_#0005`
⇒ 换的是**电脑侧插口**，不是「板子↔转接板」的排线。

因此 2T4R 静默**不是** USB 口或转接芯片的问题，而在 2T4R 链路本身：
供电、转接板的 VCC 跳线（3.3 V / 5 V）、线序（FTDI RX ↔ 板 TX）、或固件状态。

### 9.2 协议差异（实测确认，不是文档抄写）

- **帧头都是 `0x55AA`** ⇒ 靠魔数**无法**区分板型。
- 真正的区分器：

| | 1T2R | 2T4R |
|---|---|---|
| 串口帧长 | **40 B**（实测间距 40） | 136 B（文档值，本次未实测到） |
| 波特率 | 921600（实测） | 1500000（文档值） |
| 串口包率 | ≈960 pkt/s（实测 37.6 KB/s ÷ 40 B） | 482 帧/s（文档值） |
| 雷达帧率 | 7.7 Hz | 1.92 Hz |

⇒ 解析时必须**显式指定 board**，不能靠自动探测帧头。

### 9.3 一个被排除的假象（方法学）

以错误波特率（1500000）打开 1T2R 时，会读到 40.4 KB/s 的**乱码**，
字节率恰好落进 1T2R 的容差带内 —— 若只看速率会**误判为正常**。
必须先过「`55AA` 帧头命中数 ≥ 4」这一关，再做速率/间距判定。

## 10. 2026-10-29 两路并发打通（2T4R 需先被唤醒）

### 10.1 2T4R 上电不自启，被上位机唤醒后持续上报

现场观察：2T4R 工作时应有指示灯亮，静默时灯不亮；厂商上位机（ONELAB）能读到数据。
实测序列：

| 状态 | COM4 @1500000 | 说明 |
|---|---|---|
| 拔插 USB 后 | **0 B** | 上电不自启 |
| ONELAB 读过一次、**关闭 ONELAB** 之后 | **65.1 KB/s 持续** | 唤醒状态**跨进程保持** |
| 全部波特率 × DTR/RTS 组合扫描（唤醒前） | 0 B | 软件侧参数不是原因 |

⇒ **2T4R 是「待机等命令」型**（固件有 `0x0003 Start` / `0x0001 Stop`，见
`docs/radar-uplink-dev113p-2t4r.md` §7.7）；1T2R 是**上电自跑**型。
灯不亮的含义是「芯片未进入测量」，不是板子坏了。

**可用的现场流程**：ONELAB 唤醒一次 → 关掉 ONELAB（**不拔 USB、不断电**）→ 脚本直接读。
该状态一直保持到断电为止。

### 10.2 两路并发实测（5 s，同时读）

| 端口 | 板型 | 波特率 | 字节率 | 串口帧长 | 通道数 | 雷达帧率 |
|---|---|---|---|---|---|---|
| COM3 | 1T2R | 921600 | 38.6 KB/s | **40 B** | **2** | 7.6 Hz |
| COM4 | 2T4R | 1500000 | 65.1 KB/s | **136 B** | **4** | 1.75 Hz |

两路**同时读、互不影响**，5 s 内各自稳定无丢帧。
工程解析链也验证通过：`dual_noise.py --stage C` 同时录制并解析出
1T2R 61 帧 / 2T4R 14 帧。

### 10.3 协议差异的完整清单（四层，不只是帧长）

| 维度 | 1T2R | 2T4R | 能否自动识别 |
|---|---|---|---|
| 帧头魔数 | `0x55AA` | `0x55AA` | **不能**（完全相同） |
| 串口帧长 | 40 B | 136 B | 能（间距） |
| **接收通道数** | **2**（`z0,z1`） | **4**（`z0..z3`） | 能（解包长度） |
| 波特率 | 921600 | 1500000 | 不能（与板型绑定） |
| 距离门数 | 8 | 32 | 能 |

⇒ **解析必须按 `make_protocol(board)` 分支**，1T2R 与 2T4R 的
`FrameAssembler.push()` 返回长度不同（2 vs 4），
用同一套解包会直接 `ValueError: too many values to unpack`。

### 10.4 2T4R 的噪底指标要注意

2T4R 单通道 `|z|` 均值 ≈ 582、峰值 ≈ 23046（1T2R 分别约 25 / 168），
DC 与强散射主导，**逐帧总能量的分位数几乎不动**（p95/p99/max 同为 140.6 dB）。
所以 2T4R 不适合照搬 1T2R 的"噪底抬升"判据；
干扰评估的主指标仍应放在 **1T2R 侧**（它是被干扰方，也是游戏的主感知源）。

## 11. 全自动干扰检测工具（周期指纹法）

### 11.1 为什么不能用"关掉一块板再对比"

2T4R 已通过 `RegisterAutoBootup = 1`（`Radar_Config.ini` L180）实现上电自启。
但**禁用 USB 只断数据链路，不断射频** —— 芯片仍按寄存器配置持续扫频。
因此"软件开关雷达"无法构造"只有 1T2R 发射"的干净对照，
A/B 对比法必然需要人工拔插，做不到无人值守。

### 11.2 改用周期指纹

2T4R 帧周期实测 **520.84 ms → 1.9199 Hz**（`radar_source.BOARD_PROFILES['2t4r']`）。
若它确实在干扰 1T2R，1T2R 的**逐帧总能量**上会叠加 1.92 Hz 的周期起伏。

流程：只录 1T2R → 逐帧能量转 dB → 减 2 s 滑动均值去慢趋势 → 加窗 FFT
→ 在 0.5–3.5 Hz 内找峰 → 比对目标频率。

全程**不关任何雷达、不拔插、不需要管理员权限**。

### 11.3 判据（提案，待小组确认）
