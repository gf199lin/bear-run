## 1. 产品目标与问题

**目标**：交付一个用**真实毫米波雷达无接触体感操作**的跑酷游戏，形成完整闭环——雷达采集 → 人体状态识别 → 游戏逻辑响应 → 计分结算。

**要解决的问题**：传统体感交互依赖摄像头，存在**隐私与光照**限制。毫米波雷达不采集图像、不受光照影响、可穿透一定遮挡，适合作为无接触交互输入。

**目标用户与场景**：课程演示场景（教师/评委观看现场演示）为主；延伸想象为居家场景下的无接触娱乐与活动监测。

**MVP 成功定义**：现场的普通观众能**在无人指导下**站到雷达前，通过身体动作完成一局游戏并看到分数。

## 3. 核心使用旅程（Core Journey）

1. **启动**：程序启动，加载雷达连接；若雷达不可用 → 提示并进入模拟器模式（见 F6）。
2. **校准（F4）**：玩家站到雷达正前方，保持约 3 秒，系统采集基准（方位角零点、能量基线），提示「校准完成」。
3. **开跑**：角色自动向前奔跑，障碍物沿 3 条车道迎面而来。
4. **操作**：
   - 身体向**左**移动一次 → 角色切到左道；
   - 身体向**右**移动一次 → 角色切到右道；
   - **跳起** → 角色跳过障碍（验证门通过时启用）；
   - **蹲下** → 角色下蹲滑过障碍（验证门通过时启用）。
5. **反馈**：每次成功识别 → 画面立即响应 + 音效；撞击障碍 → 扣 1 条命 + 视觉/音效反馈。
6. **结算**：3 条命耗尽 → 展示本局距离得分、最高分、重开按钮。
7. **重开**：一键回到步骤 3（无需重新校准，除非玩家位置改变）。

## 4. MVP 范围（In Scope）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| F1 | **左 / 中 / 右 状态识别** | **P0（死保）** | 水平方位角分区 + 动作触发判定（移动一次切一道） |
| F2 | **完整游戏闭环** | **P0（死保）** | 开始 → 奔跑 → 换道/跳跃/下蹲 → 撞障碍扣命 → 结算 → 重开 |
| F3 | **开局校准** | P1 | 站正前方约 3 秒完成基准采集 |
| F4 | **难度递增** | P2（先砍） | 奔跑速度随距离分段加快，设上限 |
| F5 | **模拟器兜底模式** | P1 | 无雷达环境可完整演示（录制回放 + 脚本化场景） |
| F6 | **数据录制与回放** | P1 | 录制真实雷达数据供离线开发与复现 |
| F7 | **跳起 / 蹲下识别** | **P1（受验证门控制）** | 见 §6：通过 T0/T1 验证才进入 MVP，否则延至 2T4R |

**砍功能顺序（沿用小组方案并明确化）**：F4 难度递增 → 音效动效 → F7 跳/蹲（若验证未过）→ **永不砍 F1+F2**。

## 5. 排除项（Out of Scope）

- 通用手势识别（画圈、比数字等符号手势）——注意：**本项目的「左/中/右/跳/蹲」属于体位状态分类，不算通用手势识别**，两者需在文档中区分措辞，避免与课程"排除手势识别"的要求冲突。
- 多目标（同时识别多人）
- 联网对战、排行榜、账号系统
- 美术打磨（使用占位素材即可）
- 移动端移植
- 生命体征检测（呼吸/心跳）

## 6. 关键技术风险与验证门（跳起 / 蹲下）

**风险**：1T2R 无垂直角通道 → **无法直接测量人体高度** → 「跳/蹲」不能靠几何测高实现。

**可尝试的间接信号**：

| 信号 | 物理依据 | 强度判断 |
|---|---|---|
| 多普勒时序包络 | 垂直运动与雷达视线成夹角时产生径向投影；起跳/下蹲的包络形状不同 | **强**（速度分辨率 0.05 m/s 足以分辨） |
| 多普勒符号 | 投影方向取决于人体部位相对视线的仰角 | 中（需几何关系确定符号） |
| 能量质心距离趋势 | 蹲下/跳起改变被照射部位，进而改变质心距离 | 弱（距离分辨率 0.68 m，需质心插值） |
| 反射能量分布变化 | 人体姿态变化导致 RCS 分布变化 | 中（需实测基线） |

**已知坑**：chirp 周期 2.02 ms → 最大不模糊速度约 **±1.53 m/s**，人跳跃垂直速度常达 1–2 m/s，投影后可能接近上限，**需实测确认是否出现速度模糊**。

**验证门（Gate）设计**：

| 级别 | 内容 | 时间盒 | 通过判据 |
|---|---|---|---|
| T0 | 跑 ONELAB `algorithm_gr`，观察内置手势算法能否识别上下动作（配置中 `UD_SpeedMin = 0.400` 暗示支持 Up/Down） | 0.5 天 | 能稳定输出上下方向事件 |
| T1 | 以 `2dfft` 模式导出距离-多普勒数据，离线分析多普勒谱宽、双峰、质心距离趋势的**可分性** | 1–2 天 | 跳/蹲样本的特征分布可线性区分（如 AUC 达标） |
| T2 | 决策点 | — | T0/T1 通过 → 1T2R 上实现；不通过 → **跳/蹲延至 2T4R**（用俯仰角测高度） |

**结论表述**：跳/蹲在 1T2R 上是**「有希望但未证实」**，本 PRD 不承诺该能力，只承诺**验证计划与决策点**。

## 7. 约束

| 类别 | 约束 |
|---|---|
| 物理 | 帧率 7.7 Hz（玩家动作后约 130–300 ms 才见反馈）；水平视场 ±45°；垂直视场 ±25° |
| 交互 | 站姿全动作；玩家须大致正对雷达；无效区域（视场外）需有提示 |
| 时间 | 10/28 中期演示，12/8 课程现场演示；小组方案为两周冲刺（10/14–10/28） |
| 合规 | 代码私有仓库；官方资料不外传；AI 使用需留**决策记录表** |
| 交付 | Git 提交记录、测试报告、Proposal、PRD、验收测试表、演示视频 |

## 8. 可观察验收标准（阈值由本项目提案，待小组确认）

> 所有阈值均标注为**提案值**，需小组在 PRD 定稿会上确认或调整。
> 状态：**尚未执行验证**——本表是计划中的验收检查，不是已完成的证据。

| # | 验收项 | 验证方法 | 提案阈值 |
|---|---|---|---|
| AC-1 | 左/中/右 识别正确率 | 正对雷达，1.0 m 处随机取位 30 次，记录识别结果 | ≥ 90% |
| AC-2 | 静止误触发率 | 玩家静站 60 s，统计误切换次数 | ≤ 2 次/分钟 |
| AC-3 | 响应延迟 | 秒表/录屏逐帧核对：人体到位 → 画面响应 | ≤ 300 ms |
| AC-4 | 游戏帧率 | 帧率显示工具 | ≥ 30 FPS |
| AC-5 | 校准耗时与成功率 | 10 次校准，记录耗时与失败次数 | ≤ 5 s，成功率 ≥ 90% |
| AC-6 | 目标丢失恢复 | 玩家走出视场再返回 | ≤ 2 s 内恢复，期间游戏自动暂停 |
| AC-7 | 模拟器兜底可用性 | **拔掉雷达**，完整跑通一局 | 全流程无崩溃、可结算 |
| AC-8 | 一局完整可玩 | 无指导的旁观者完成一局 | 3 条命流程完整、分数正确显示 |
| AC-9 | 数据录制回放一致 | 回放录制数据，检查状态序列一致性 | 与实时结果一致率 ≥ 90% |
| AC-10 | 跳/蹲识别（**条件性**） | 依据 §6 验证门 | 仅在 T0/T1 通过后定义阈值 |
