# DEV202H 上行数据协议（实机逆向结果）

- 版本：v1.0 ｜ 日期：2026-10-15 ｜ 设备：DEV202H / ICL1122 / 1T2R
- 状态：**已实机验证**。本文所有字段均以「厂商固件源码 + 实机抓包」双向交叉确认；未验证项集中在 §7，不得当作已实现能力使用。
- 适用场景：自行取数做算法（`DriverType = data_transfer`），即本项目路线。

| 项 | 值 | 证据 |

## 2. 串口包封装（Wrapper）

每个串口包 **52 字节 = 8 B 头 + 40 B 雷达帧 + 4 B 尾**。

| 偏移 | 长度 | 字段 | 实测取值 |
|---|---|---|---|
| 0–3 | 4 | 包头 | `49 43 4C 48`（ASCII **`ICLH`**） |
| 4–5 | 2 | **载荷长度**（uint16 **小端**） | `0x0028` = 40 |
| 6–7 | 2 | **序号/计数**（uint16 小端） | 实测在 `0x0000` / `0x0001` 间交替，逐包增量集合 {0, 128, 256, 65280} |
| 8–47 | 40 | 雷达数据帧（见 §3） | — |
| 48–51 | 4 | 包尾 | `49 43 4C 54`（ASCII **`ICLT`**） |

**固件佐证**：`WRAPPER_HEAD_LEN = 8`、`WRAPPER_TAIL_LEN = 4`、`WRAPPER_LEN = 12`
→ 位于 `App/common/inc/dataprocess.h` **L67–L69**（8 + 4 = 12 字节封装，与实测完全一致）。

> 实机统计（`cap.bin`，154665 B）：解析 2974 包，其中 **2974/2974 个包**的尾 4 字节均为 `ICLT`；长度字段取值集合为 {40, 4}。

## 3. 40 字节雷达数据帧

### 3.1 结构

| 偏移 | 长度 | 字段 | 实测 |
|---|---|---|---|
| 0 | 1 | **`0xAA`** 帧起始 | 恒为 `AA` |
| 1 | 1 | **ID**：高半字节 = 接收通道 | `0x30` = RX0，`0xB0` = RX1 |
| 2 | 1 | **X1**：携带 chirp 序号高位 | — |
| 3 | 1 | **X2** | 实测恒为 `0x09`（语义未验证） |
| 4–35 | 32 | **载荷**：8 个复数值，各为 `int16 实部 + int16 虚部`（**大端**） | 见 §3.3 |
| 36–38 | 3 | 未识别尾字段 | 语义未验证 |
| 39 | 1 | **`0x55`** 帧结束 | 恒在帧内偏移 39 |

**长度自洽校验**：固件 `dataprocess.c` **L771**
`radarPara->dataLen = Radar_GetFftPoint() * 2 * 2 + SPI_FRAME_HLEN + SPI_FRAME_TLEN  /*16 bit, IQ*/`
即 8（1DFFT 输出点数）× 2（字节）× 2（I/Q）+ 4 + 4 = **40 字节**，与实测帧长一致。

`SPI_FRAME_HLEN = 4` / `SPI_FRAME_TLEN = 4` 见 `Middleware/platform/DEV202H/inc/py32_spi.h` **L27–L29**。

### 3.2 chirp 序号的拼装

```
chirpIndex = ((ID & 0x0F) << 4) | ((X1 & 0xF0) >> 4)      // 实测取值 0..63
```

**固件佐证**：`dataprocess.c` **L71**（`(data & CHIRP_INDEX_NEW_MASK0) << CHIRP_INDEX_NEW_POS0`）、**L188**（`MASK2 << POS2 | MASK1 >> POS1`）；宏定义见 `dataprocess.h` **L60–L65**（`POS0 = 4, MASK0 = 0x0F`；`POS1 = 4, MASK1 = 0xF0`；`POS2 = 5, MASK2 = 0x08`）。

> `MASK2 = 0x08` 对应 `X1` 的 bit3，实测该位恒为 0，因此该项在本机数据中恒为 0；换用其它配置时必须重新确认。

### 3.3 载荷字节序：**大端**

`int16` 为大端（高字节在前）。判定依据（三重）：

1. **固件**：`dataprocess.c` 中 1DFFT 分支取数并做 `[0]↔[1]`、`[2]↔[3]` 字节交换，符合"线上大端、MCU 小端"的转换约定；
2. **数值合理性**：`cap.bin` 首包按大端解出 `-8+31j, 3-21j, -2+9j, 9+3j, -10-9j, 6+3j, 2-1j, -4+4j`（幅度 ~10–30，符合 1DFFT 输出量级）；
3. **反证**：按小端解读同一字节得 `-1793 / 7936` 等值，与 `RawSampleSize = 256` 的量级不符。

### 3.4 组帧规则

- **1 个雷达帧 = 128 个串口包 = 64 chirp × 2 RX**；
- 包序为逐 chirp 交错：`ch0(n) → ch1(n) → ch0(n+1) → …`，同一 chirp 的两个 RX 偶有先后对调；
- 因包内**无帧号**，入帧边界依赖 **chirp 序号回绕**（由 63 → 0 判定新帧开始）与**超时兜底**（超过 `2 × chirps × 2` 个包仍未闭帧则丢弃残缺帧）。实机验证：`cap.bin` 中拼出 22 个完整帧、丢弃 1 个残缺帧。

## 5. 下行命令协议（仅在改配置时使用）

厂商《ICL_Radar Serial Communication Protocol V2.3》定义的上位机→雷达命令：

- 帧头 `0xFAFBFCFD`，帧尾 `0x01020304`；
- 命令模式开关：`0x00FF` / `0x00FE`；系统模式 `0x0012`。

本项目软件**当前未使用**该协议。厂商文档属保密材料，不入库（`.gitignore` 已排除 `uploads/`、`*.zip`）。

> **2026-10-15 更正（依据固件源码，非厂商文档）**：本节原先只有厂商手册层面的描述，
> 现经实读固件补齐，并以固件为准：
>
> - 帧格式：帧头 **`FD FC FB FA`** + `LEN(u16LE)` + `[cmdType(u16LE) + cmdData]` + 帧尾 **`04 03 02 01`**
>   （与上文 §5 旧述的 "0xFAFBFCFD / 0x01020304" 是同一串字节的**字节序**写法差异，以固件解析顺序为准）。
> - 常量：`CMD_BUF_LEN=54`、`CMD_TYPE_LEN=2`、`CMD_LEN_MAX=64`、`CMD_REG_MAX=25`。
> - `WRITE_REG_CMD=0x0001`、`READ_REG_CMD=0x0002`；`DoWriteReg` **要求先进入命令模式**，
>   `cmdData[0]` 为 **7 位设备地址**（固件内部左移 1 位后再比较）；单帧最多
>   `(54-2-2)/4 = 12` 条寄存器。
> - ACK：`cmdType = 原命令 | 0x0100`，随后 `status(u16LE)`（`0=ACK_OK`）。
> - 来源：`.deepworks/tmp/dev202h/DEV202H/App/common/src/cmdprocess.c`（`DoWriteReg`、解析状态机）、
>   `inc/cmdprocess.h`（常量与 ACK 帧示例）。
> - 注意：**上电即出流**（§1）仍然成立，即"出点云"不依赖下行命令；但"改配置 / 停机"必须走下行命令，
>   二者不矛盾。详见 `radar-hardware-stop-plan.md`、`radar-control-and-actions.md`。

## 7. 未验证项（不得当作已知）

1. 长度字段取值 `4` 的包（偶发）——语义未知，疑似空帧/同步帧；
2. 序号字段（偏移 6–7）的精确语义：实测值与总包序不同步，递增模式未解释；
3. `X2 = 0x09` 恒定的含义；
4. 帧内偏移 36–38 三个字节的含义；
5. **距离 > 1.4 m 的目标从未在实机数据中出现过**（见 §8），因此**距离门与真实米数的对应关系尚未经真值验证**；
6. **方位角符号与线性度仅在软件合成闭环中验证过（误差 0.29°），真机真值未验证**。

## 8. 与算法相关的实机数据性质（补充观测）

对 11 分钟实机连续录制（5078 帧）做离线分析，得到：

- 去静态杂波后的多普勒谱呈**以 0 为中心的 sinc 型滚降**（相邻多普普勒单元 ~16–20 dB 衰减）——若 chirp 顺序或字节序有误，该谱会变平；**这是字节序与组帧顺序正确的独立佐证**；
- 距离向功率随距离单调衰减（bin0 最强，bin7 约 −31 dB）；
- 全部强反射集中在 **r ≤ 1.4 m（bin0/bin1）**，|v| ≤ 0.19 m/s，bin3（>2 m）以上几乎无能量。

**解释**：录制期间雷达前方始终是 0–1.4 m 的近距强反射（操作者/桌面/显示器）。这不构成"距离定标已通过"的证据。
