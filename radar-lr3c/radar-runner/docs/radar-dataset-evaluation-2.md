# 两批新雷达数据的可用性评估（跳/蹲 + 左右）

> 评估对象：`game-training-data.zip`（DEV113P 跳/蹲，2026-10-21）与 `lr-move-*`（DEV202H 1T2R 左右，2026-10-21）
> 结论时间：2026-10-21　　评估脚本：`.deepworks/tmp/gtd/_work/*.py`（可重跑复现）
> 一句话结论：**两批数据都不能用来标定/验证「上下左右」判定**；跳/蹲数据可退化为「上游误报率基线」使用，左右数据必须重采。

---

## 0. 结论速览

| 数据集 | 想用它做什么 | 实测结果 | 能否用 |
|---|---|---|---|
| 跳/蹲 DEV113P（3 take，266/265/265 帧） | 定出跳/蹲判定阈值 | 等长窗规则 TPR 87% 但 **FPR 89%**；单帧特征 AUC ≤ 0.63 | ❌ 不能定阈值 |
| 同上 | 做「静息误报率」基线 | 真实负样本 523 帧上误报率 **跳 39.4% / 蹲 54.3%** | ✅ 可用（已用于 v2 探针阈值） |
| 左右 DEV202H lr-move（3092 帧，30 动作） | 定出左右方向符号 | 方向符号准确率 **53.3%**（16/30）；分站位现场校准后最好也只有 60% | ❌ 不能定符号 |
| 同上 | 定出「走了多远算一步」 | RIGHT 15 次里只有 1 次横向位移 ≥ 0.42 m | ❌ 幅度也不够 |

> 记录：用户原以为组员已交付【左右上下】四方向数据；实际 zip 内只有**跳/蹲**两个动作，左右仍是上一批 `lr-move`。

## 1. 数据集一：跳/蹲（DEV113P）

### 1.1 基本信息

| 项 | 值 |
|---|---|
| 帧率 | **1.92 Hz**（帧周期 **0.521 s**，`frame_period_s=0.52084`）|
| 录制长度 | 131 s 脚本 / 每 take ≈ 138 s |
| 文件 | `radar_raw_1792576640965.bin`(A)、`..._1792576891518.bin`(B)、`..._1792577686397.bin`(C) |
| 动作窗 | 跳 39 个 + 蹲 39 个（各 13×3 take，含 6 个连招）|
| 站位 | A 0.88 m / B 0.70 m / C 1.06 m（`person_gate` 5/4/6 → **距离门被锁死，全程无竖直方向位移信号**）|
| 对时 | `template_correlation`，**score 仅 0.198 / 0.271 / 0.204** → 对时本身不可信 |
| 备注 | B 标注「采集时雷达板有轻微倾斜（用户报备）」|

### 1.2 致命问题一：标注帧数太少，动作被帧率淹没

动作时长 4.00 s，但 1.92 Hz 只给到 **约 2 帧**：

| 动作 | 标注帧数 n | min | 中位 | max |
|---|---|---|---|---|
| jump | 39 | 1 | **2** | 6 |
| crouch | 39 | 3 | **4** | 6 |

跳（≈0.5 s 的腾空）在 0.521 s 的采样间隔下基本**采不到**，多数只落在 1~2 帧上。

### 1.3 致命问题二：README 判据零判别力

按 `README` 的原始判据在**等长窗（W=5 帧）**上复算，跳/蹲规则各自对自己的窗和别人的窗误报几乎一样高：

| 规则 | TPR（本方窗） | 误报（对方窗） | FPR（静站窗） | FPR（全部负窗） |
|---|---|---|---|---|
| 跳 `min(dev1) < -18` | 34/39 = **87.2%** | 31/39 = **79.5%** | 292/327 = **89.3%** | 428/471 = **90.9%** |
| 蹲 `count(dev1 >= +12) >= 2` | 34/39 = 87.2% | 27/39 = **69.2%** | 278/327 = **85.0%** | 397/471 = 84.3% |

把窗口收紧到单帧（W=1）后，FPR 才能压到 40% 左右，但 TPR 也一起掉到 41%：

| W | 阈值 | TPR | FPR（非 idle 负） | FPR（全负） |
|---|---|---|---|---|
| 1 | -18 | 16/39 = 41.0% | 132/339 = 38.9% | 195/483 = 40.4% |
| 1 | -40 | 14/39 = 35.9% | 113/339 = 33.3% | 170/483 = 35.2% |
| 1 | -120 | 6/39 = 15.4% | 55/339 = 16.2% | 84/483 = 17.4% |

**判据等于是掷硬币**：跳规则打到蹲窗 79.5%，蹲规则打到跳窗 69.2%。

### 1.4 致命问题三：`dev1` 是白噪声

| take | n | mean | std | lag1 自相关 | lag2 |
|---|---|---|---|---|---|
| A | 113 | 38.8 | 108.0 | **-0.031** | +0.044 |
| B | 113 | 5.7 | 102.1 | **-0.118** | +0.049 |
| C | 113 | -8.8 | 102.8 | **-0.126** | -0.048 |

自相关 ≈ 0 → 相邻帧之间没有相关性，即**帧间无记忆**，与「人做动作会产生连续多帧的仰角变化」完全不符，符合纯噪声特征。

### 1.5 致命问题四：混淆矩阵之外，单帧特征也没有信息

对所有单帧物理量做「动作帧 vs 负样本帧」AUC：

| 特征 | AUC（跳） | AUC（蹲） |
|---|---|---|
| dev1 | 0.516 | 0.506 |
| act（运动能量） | 0.547 | 0.543 |
| db | 0.524 | 0.503 |
| az0 | 0.567 | 0.547 |
| el0 | 0.547 | 0.520 |
| dopcent | 0.514 | 0.538 |
| dopsum | 0.516 | 0.520 |
| dopargmax | 0.522 | 0.547 |
| rhicent | 0.525 | 0.565 |
| rhisum | 0.514 | **0.625** |
| rhiargmax | 0.546 | 0.587 |

**全部 ≤ 0.63**（0.5 = 无判别力）。唯一的 `act` 分布对比（跳 78 帧 / 蹲 78 帧 / 负样本 960 帧）：

```
jump帧    p05=0.84 p25=0.93 med=0.95 p75=0.96 p95=0.97
crouch帧  p05=0.86 p25=0.91 med=0.94 p75=0.95 p95=0.97
负样本帧   p05=0.84 p25=0.91 med=0.94 p75=0.96 p95=0.97
```

三条分布**逐分位完全重合**。

### 1.6 有用的一面：真实负样本误报率

把 README 判据逐帧化（取消窗口），在 **523 帧真实负样本**上实测静息误报率：

- 跳：**39.4%**
- 蹲：**54.3%**

这正是 v2 教程「质量探针」阈值的来源：玩家在第 1~3 步本不该跳/蹲，若每 24 帧里误报超过 2 次（≈8.3%）或占比超过 6%，就判定上游不可信并停用跳/蹲。**这个 39.4%/54.3% 是这批数据唯一的直接产出。**

## 2. 数据集二：左右（DEV202H 1T2R，`lr-move`）

### 2.1 基本信息

| 段 | 站位 | 帧数 | 帧率 | 动作 | 检出率 |
|---|---|---|---|---|---|
| `seg_00.70.bin` | 0.70 m | 1031 | 7.72 Hz | 5 左 + 5 右 | 44.7% |
| `seg_00.85.bin` | 0.85 m | 1031 | 7.72 Hz | 5 左 + 5 右 | 48.3% |
| `seg_01.00.bin` | 1.00 m | 1030 | 7.72 Hz | 5 左 + 5 右 | 31.8% |
| 合计 | | 3092 | | **15 左 + 15 右** | **41.6%** |

交付方自己的 README 已记录：LEFT 一致 13/15，**RIGHT 只有 3/15**；根因是**采集时雷达没有瞄准人**（静息主回波方位角 ≈ +40°，横向偏 1.1~1.5 m，贴 ±45° 视场边缘），人稍向外走就直接出视场。

### 2.2 我方复算：方向符号 = 掷硬币

| 指标 | 值 |
|---|---|
| `px_delta` 符号与人工标签一致 | **16/30 = 53.3%** |
| 分站位（原始判向） | d00.70 左 4/5、右 **0/5**；d00.85 左 5/5、右 3/5；d01.00 左 4/5、右 **0/5** |

### 2.3 关键否证：**不是**「基线漂移/整体符号反转」

若是单纯的符号装反，去基线后左/右应各自朝相反方向分开。实测去基线位移（米）：

| 站位 | LEFT 去基线位移（5 次） | RIGHT 去基线位移（5 次） | 静息基线 |
|---|---|---|---|
| d00.70 | -1.297 / -0.249 / -0.528 / -0.685 / -0.564 | **-0.156 / -0.154 / -0.099 / -0.141 / -0.074** | +0.623 |
| d00.85 | -0.057 / -0.290 / -0.003 / +0.024 / -0.744 | -0.022 / -0.213 / -0.149 / -0.166 / -0.152 | +0.620 |
| d01.00 | （LEFT 侧存在同样重叠）| 与 LEFT 同号 | +1.034 |

- 静息基线本身**站位内很稳**（p25~p75 仅 ±0.06 m），说明基线不是噪声问题，而是**随站位整体平移**（+0.62 / +0.62 / +1.03 m）。
- 但去掉基线后，**RIGHT 的位移依旧是负的、而且很小（0.07~0.16 m）** —— 屏幕上根本没有「向右走」的运动，谈不上符号。
- 所以**任何一次整体符号翻转都救不了**，只能重采。

分站位用「第一对 LEFT/RIGHT 现场学符号、再套到其余 8 次」的做法（就是我们教程第 2/3 步想做的事）：

| 站位 | 学到 sign | 其余动作方向正确 |
|---|---|---|
| d00.70 | -1 | 5/10 = 50% |
| d00.85 | +1 | 6/10 = 60% |
| d01.00 | +1 | 2/10 = 20% |

### 2.4 幅度也不够

教程第 2/3 步要求相对基线位移 ≥ `moveDelta=0.35`（≈0.42 m）：

| 方向 | 中位 \|Δpx\| | 达到 0.42 m 的动作 |
|---|---|---|
| LEFT | 0.249 m | 6/15 |
| RIGHT | 0.154 m | **1/15** |

即使方向蒙对，也**判不出「人真的走了一步」**。

## 3. 对产品的直接含义

1. **不能靠「更强的识别」解决** —— 数据里没有可提取的信号（跳/蹲判据零判别力、左右位移不成立）。所以教程 v2 不做「识别升级」，改做**质量探针 + 拒绝回退**（见 `docs/radar-calib-v2.md`）。
2. **必须有一步「雷达原始数据质量门」**：上游给的跳/蹲字段在静息状态下 39.4%/54.3% 误报，直接进游戏会导致角色随机乱跳。v2 用探针把这种上游挡在门外，让玩家用键盘继续玩。
3. **左右键位只能等重采**（补采要求见 `outputs/雷达数据补采方案.md`）。
4. 相机/键盘路线不受影响。
